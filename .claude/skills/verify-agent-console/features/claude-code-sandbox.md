# Агент на Claude Code в песочнице

Агент конструктора может работать не на встроенном цикле Pi, а на Claude Code. Claude Code запускается внутри VM LiteBox сессии как ACP-агент `claude-acp` (npm-пакет `@agentclientprotocol/claude-agent-acp`, внутри него Claude Code из `@anthropic-ai/claude-agent-sdk`).
main-node ведёт ACP-сессию по stdio процесса в VM, переводит её обновления в события сессии и показывает ход в консоли как обычный: реплика, карточки инструментов Claude Code (`Write`, `Read`, `Bash` …), ответ, файлы сессии.
С 2026-10-16 ключа модели в VM нет. Модель агента берётся из карточки модели (или по ключу сервера), на каждом ходе main-node выпускает токен песочницы `oma_sbx_` и передаёт адаптеру Claude адрес прокси своей сессии (`prepareAcpTurnInference` в `apps/main-node/src/lib/models-harness-wiring.ts`). Claude Code ходит в `<шлюз>/v1/oma/inference-proxy/<сессия>/anthropic` с этим токеном, прокси подставляет ключ карточки и меняет `model` на `wire_model`. Ключи моделей из хранилища сессии сервер в VM не кладёт (`skipModelKeys` в `apps/main-node/src/lib/node-managed-vault-env.ts`), другие переменные хранилища доходят. Guard на `POST /v1/agents` не сохраняет агента с ключом или адресом модели в env.

## Sub-features

- `cc-model-card`: карточки моделей из консоли: Anthropic с адресом фейка (подходит Claude Code) и OpenAI (протоколы OpenAI, Claude Code не подходит); ключ проверен при создании.
- `cc-environment`: окружение с npm-пакетом `@agentclientprotocol/claude-agent-acp` (консоль: карточка окружения, «Добавить пакет»).
- `cc-vault`: хранилище с учётными данными «переменная окружения» `ANTHROPIC_API_KEY` (до VM дойти не должен) и обычной переменной (API; консоль показывает).
- `cc-guard`: guard на `POST /v1/agents` отвечает 400 на секрет и ключ модели в env агента, неизвестный harness и несовместимую модель; агент не создаётся, окно агента показывает отказ.
- `cc-agent`: агент из формы: Harness «Claude Code в песочнице», модель карточки, блок `_oma.acp` из каталога, список `allow` расширен в YAML той же формы.
- `cc-incompatible-model`: в форме при Claude Code несовместимая модель видна, но выключена с причиной (строка, `title`, `aria-describedby`); смена Harness заменяет такую модель.
- `cc-session`: сессия с этим агентом, окружением и хранилищем (окно «Новая сессия»).
- `cc-turn`: ход: Claude Code в VM пишет и читает `verify.txt` в рабочей папке, отвечает; события сессии в порядке.
- `cc-permissions`: инструмент вне списка `allow` (Bash с записью) отклоняется: режима обхода разрешений нет.
- `cc-tool-cards`: строки вызовов Claude Code `Write` и `Read` в разговоре, раскрытый `Read` с выводом.
- `cc-files`: `verify.txt` на вкладке «Ресурсы» инспектора сессии, в `GET /v1/sessions/:id/outputs` и на хосте.
- `cc-proxy`: Claude Code ходит в модель через прокси сервера: в каждом запросе ключ карточки, без токена хода, `model` = `wire_model` карточки.
- `cc-no-key-in-vm`: у `claude-agent-acp` в VM адрес прокси своей сессии и токен хода `oma_sbx_`, ключа модели нет (ни ключа карточки, ни ключа из хранилища), сервер записал `model_key_skipped`.
- `cc-multi-turn`: второй ход в той же сессии: новый `claude-agent-acp` возобновляет ACP-сессию первого хода, процесс первого хода закрыт (в VM один `claude-agent-acp`), на хосте его нет.
- `cc-archive`: архив сессии останавливает VM.
- `cc-real-key`: ход с настоящим ключом API Anthropic в карточке модели (`VERIFY_CC_MODE=real`). Включается только явно.

## How to get to it (user POV)

- «Окружения» → окружение → «Добавить пакет», менеджер `npm`, «Пакеты и версии» `@agentclientprotocol/claude-agent-acp@0.91.0` (версия закреплена: без неё npm ставит последнюю при каждом старте VM) → «Сохранить изменения». Сеть «Без ограничений» (или «Ограниченный» с хостами из Gotchas).
- «Карточки моделей» → «Новая карточка модели»: провайдер Anthropic, ключ API, модель, адрес. Ключ остаётся на сервере, Claude Code его не видит. Без карточки подойдёт модель по `ANTHROPIC_API_KEY` сервера.
- «Хранилища секретов» → хранилище. Учётные данные типа «переменная окружения» консоль только показывает (`pages/VaultDetail.tsx:78`), создаются они запросом `POST /v1/vaults/:id/credentials` с `auth.type: "environment_variable"`. Ключ модели в хранилище больше не нужен: до VM он не доходит.
- «Агенты» → «Новый агент» → «Пустой агент» → раздел «Основное»: Harness «Claude Code в песочнице», модель из группы «Карточки моделей» → при необходимости список `allow` в `OMA_CLAUDE_SETTINGS` в режиме «YAML» → «Создать агента».
- «Сессии» → «Новая сессия»: агент, окружение, при необходимости галочка хранилища в «Хранилища секретов» → «Создать» → сообщение.

## Gotchas

- **Диск VM.** У `node:22-bookworm` корневой диск VM BoxLite 0.9.0 занимает 1,3 ГБ, свободно ~120 МБ, а пакет весит ~330 МБ (из них 255 МБ приходится на `claude-agent-sdk-linux-x64`). Без `LITEBOX_DISK_SIZE_GB` (адаптер: `diskSizeGb`, `packages/sandbox-adapter-litebox/src/litebox.ts`) установка падает с `ENOSPC`. Сценарий ставит 4 ГБ (`VERIFY_LITEBOX_DISK_SIZE_GB=4`). Установка занимает от 23 до 30 с при каждом старте VM.
- **Хост из VM.** `host.boxlite.internal` → `192.168.127.254` → `127.0.0.1` хоста (gvproxy BoxLite), запрос к хосту приходит с `127.0.0.1`. `192.168.127.1` (шлюз) на порты хоста не отвечает. Поэтому `launch.sh` задаёт серверу `SANDBOX_GATEWAY_BASE_URL=http://host.boxlite.internal:<VERIFY_PORT>`: без неё сервер взял бы `PUBLIC_BASE_URL` (`http://127.0.0.1:<порт>`), а `127.0.0.1` из VM ведёт в саму VM.
- **Модель только через прокси.** Адаптер Claude (`packages/harness-inference-adapters/src/adapters/claude.ts`) ставит `ANTHROPIC_BASE_URL` на прокси сессии, `ANTHROPIC_AUTH_TOKEN` на токен хода, `ANTHROPIC_MODEL` и модели по умолчанию на handle агента и убирает `ANTHROPIC_API_KEY` из env запуска. До 2026-10-16 сценарий клал `ANTHROPIC_BASE_URL` фейка в env агента и ключ в хранилище; теперь guard такого агента не сохранит (`server_name`), а ключ модели из хранилища сервер пропускает.
- **Разрешения.** `acp-sandbox` не передаёт обработчик `requestPermission`, поэтому любой запрос разрешения Claude Code получает `cancelled` и инструмент отклоняется. Нужные инструменты разрешаются списком `permissions.allow` в `settings.json` Claude Code. Обёртка `sh -c` из YAML пишет его в `$CLAUDE_CONFIG_DIR` (его задаёт профиль `claude-code`, `packages/acp-runtime/src/native-state.ts`). `claude-agent-acp` читает настройки `user`, `project`, `local`. Команды только для чтения (`echo`, `ls`, `cat`) Claude Code выполняет без запроса, поэтому контрольная команда: `touch`.
- **Отказ инструмента.** ACP-агент сообщает неудачный вызов как `tool_call_update{status: "failed"}`, обычно без вывода. До правки 2026-10-16 `AcpTranslator` писал только текст `(status: failed)` без `is_error`, и консоль рисовала у отклонённого Bash зелёное «Готово» (прогон `20261016-011901`, `screens/14-cc-turn-tool-cards.png`). Теперь `is_error: true` (`apps/agent/src/harness/acp-translate.ts`, `#emitToolResult`; тест `apps/main-node/test/acp-translate-failed-tool.test.ts`). Причину отказа событие не несёт.
- **Ключи `input` в API.** `GET /v1/sessions/:id/events` отдаёт `input` инструментов Claude Code в camelCase: `file_path` → `filePath`. Проверки читают оба ключа (`filePathOf`).
- **Пустой ход.** До правки 2026-10-16 main-node передавал харнессу пустой `userMessage`, и `acp-sandbox` падал с `Could not extract text from user message — empty turn` (прогон `20261016-011625`). Теперь текст берётся из принятых событий хода (`apps/main-node/src/lib/node-managed-harness-user-message.ts`).
- **`_oma.acp.agent.id: claude-acp` обязателен** при `command: sh`: профиль состояния выбирается по id или по имени команды, а имя тут `sh`.
- **Рабочая папка.** `cwd: /mnt/session/outputs` делает рабочую папку Claude Code папкой выводов сессии: всё, что он там пишет, попадает в файлы сессии (вкладка «Ресурсы» инспектора). Claude Code 2.1 сообщает её модели строкой `Primary working directory: …` в сообщении с ролью `system` после реплики пользователя, фейк ищет её по всем сообщениям.
- **Системный промпт агента до Claude Code не доходит.** `AcpSandboxHarness.onSessionInit` пишет его в `/workspace/AGENTS.md`, но main-node этот хук не вызывает, а Claude Code читает `CLAUDE.md`.
- **Каждый ход запускает новый процесс.** main-node создаёт харнесс заново на каждый ход (`buildHarness` в `apps/main-node/src/modules/node-managed.ts`). До 2026-10-16 он не вызывал `dispose`, и прежний `claude-agent-acp` оставался в VM до её остановки. Теперь `runHarnessForTurn` (`apps/main-node/src/lib/node-managed-harness-turn.ts`) после хода вызывает `dispose("shutdown")`: процесс закрывается, ACP-сессия и чекпойнт остаются в VM, и следующий ход возобновляет её (`cc.turn2_resumed`, `cc.acp_in_vm_single`). Сессионного владельца харнесса, как `HarnessLease` upstream (`apps/agent/src/harness/registry.ts`), у main-node нет, поэтому каждый ход платит за старт `claude-agent-acp`.
- **Сигналы процессу в VM не доходят (BoxLite 0.9.0).** `signal()` и `kill()` потокового exec не завершаются и ничего не доставляют: проверено в VM 2026-10-16, процесс живёт до остановки VM. Поэтому `dispose` первого хода оставлял `claude-agent-acp` живым (прогон `20261016-024343`: во втором ходе в VM два процесса, PID 24 и 83). Адаптер LiteBox при `kill` сначала закрывает stdin (`spawnDuplexProcess` в `litebox.ts`): `claude-agent-acp` выходит по EOF. Если процесс пережил и EOF, и сигнал, в логе сервера предупреждение `duplex process … did not exit after …`. После этой правки прогон `20261016-041100`: во втором ходе в VM один `claude-agent-acp` (PID 92), на хосте его нет (`cc.acp_in_vm_single`, `cc.acp_not_on_host`).
- **Вывод Bash Claude Code в событиях не виден.** `agent.tool_result` для `Bash` содержит только `(status: completed)` или `(status: failed)`: ACP присылает вывод терминалом, `AcpTranslator` его не переносит. Карточка Bash в консоли без вывода. Поэтому `cc.acp_in_vm_single` и `cc.vm_env_*` берут вывод `ps` из запроса Claude Code к фейку (`acp_lines` и `env` в `api/cc-fake-model-requests.json`), а в режиме real пишут «не проверено». `Read` и `Write` вывод переносят.
- **Окружение процесса через `ps eww`.** `ps eww -o args= -p <pid>` печатает команду и через пробел переменные `NAME=value`; значение с пробелом режется. Для имён, адреса прокси и sha256 ключей этого хватает. Читать `/proc/<pid>/environ` пришлось бы через `cat` и `tr`, а их нет в списке `allow`.
- **Переменные хранилища в VM открыты.** Официальный контракт `environment_variable` подставляет секрет на выходе (в VM только заглушка). На main-node такого прокси нет: `applyVaultEnvironment` (`apps/main-node/src/lib/node-managed-vault-env.ts`) кладёт само значение в окружение песочницы (`setEnvVars`), его видят Claude Code, его инструменты и bash (`VERIFY_VAULT_NOTE`, строка «внимание» `cc.vault_plain_in_vm`). Ключи моделей (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `OPENAI_API_KEY` и другие) и переменные прокси сервер пропускает (`skipModelKeys`, предупреждение `main-node.vault_env.model_key_skipped` с именем без значения). Переменные хранилища получает только харнесс `acp-sandbox`: default-харнесс (Pi) их в песочнице не получает, скрипт установки пакетов окружения тоже (ему адаптер LiteBox передаёт только переменные прокси). `networking` и `injection_location` учётных данных не применяются, о каждой такой учётной записи сервер пишет предупреждение `main-node.vault_env.policy_not_enforced` (без значения).
- **Сеть «Ограниченный»** не проверялась. Понадобятся `registry.npmjs.org` (разрешение менеджерам пакетов) и хост шлюза в разрешённых. Фильтр BoxLite 0.9.0 пропускает по имени только порты 80 и 443, шлюз на порту 8795 из такой сети недоступен.
