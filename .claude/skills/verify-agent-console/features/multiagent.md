# Мультиагент: подтверждение в потоке субагента, предел сессии, блок multiagent_20261001

Основной агент передаёт задачу субагенту. Если bash субагента стоит на `always_ask`, поток субагента ждёт человека, сессия встаёт на `requires_action`. Одно «Разрешить» исполняет вызов один раз в потоке субагента, субагент продолжает ход, а основной поток получает его отчёт событием `agent.thread_message_received`. Сессия считает токены всех потоков и ходы субагентов. На пределе ход встаёт с `budget_reached`, шапка пишет простую заметку без чисел и даёт кнопку «Поднять предел», после подъёма ход продолжается. Агент принимает блок `multiagent_20261001` рядом с `coordinator`, форма его показывает и сохраняет, делегирование идёт так же, как у `coordinator`.
Проект: `docs/plans/multiagent.md`, шаг 1 (3.1), раздел 3.Б и шаг 2 (3.2). План называл сценарий шага 1 `journey-subagent-confirm.mjs`, это `scripts/journey-multiagent.mjs`. Подфункции этого файла считает сценарий `multiagent`, главный сценарий их не считает.

## Sub-features

- `subagent-confirm-waits`: реплика из консоли, основной агент с блоком `coordinator` вызывает `call_agent_<id>`, bash субагента на `always_ask` ждёт: поток субагента и сессия встали на `requires_action` с `event_ids` вызова, `call_agent` вернул текст ожидания, bash не исполнялся; «Разрешить» с чужим `session_thread_id` получает 400.
- `subagent-confirm-ui`: страница сессии с делегированием показывает ход, во вкладке «Потоки» выбран поток субагента, над полем ввода блок «Ожидает подтверждения» с bash и кнопкой «Разрешить», живьём и после свежей загрузки.
- `subagent-confirm-allow`: «Разрешить» исполняет bash один раз в потоке субагента: один `agent.tool_result` с его потоком, одна строка в файле на хосте, субагент продолжает ход без нового сообщения и кончает `end_turn`.
- `subagent-confirm-report`: основной поток получает `agent.thread_message_received` с ответом субагента, основная модель читает отчёт сообщением пользователя (`last_user_text` в журнале фейка), сессия кончает `end_turn`.
- `subagent-confirm-repeat`: второе «Разрешить» по API без `session_thread_id` на исполненный bash: сервер берёт поток из вызова, bash не исполняется снова, отчёта и хода модели нет.
- `session-limit-count`: `_oma.limits` сессии с делегированием: `used_tokens` равен 15 на каждый запрос к фейку во всех потоках, `used_child_turns` равен числу запусков потока субагента, оба растут после хода субагента.
- `session-limit-stop`: сессия с `max_tokens: 1` встаёт на `budget_reached` после первого запроса и bash, без повтора и `session.error`; `user.message` по API получает 400 с подсказкой про `_oma.limits`.
- `session-limit-ui`: шапка пишет «Предел работы сессии исчерпан, агент остановился.» и кнопку «Поднять предел», без чисел, токенов и денег, на 1280 и 390; отправка реплики из консоли даёт уведомление и на сервер не уходит.
- `session-limit-raise`: «Поднять предел» поднимает оба предела вдвое, ход продолжается без новой реплики и кончается ответом, bash не повторяется, заметка уходит.
- `multiagent-block-api`: агент с блоком `multiagent_20261001` по API: умолчания, закрепление ссылок версией, `self` читается как сам агент; три отказа 400.
- `multiagent-block-form`: вкладка «Мультиагентность» формы агента нового типа на 1280 и 390, «Сохранить изменения» проходит и не меняет блок, `self` в `workflows` остаётся самим агентом.
- `multiagent-block-delegation`: сессия агента нового типа хранит тип, субагент списка лежит в ней целиком, делегирование с подтверждением идёт как у `coordinator`, у модели те же инструменты `call_agent_*`.

## How to get to it (user POV)

- Окно «Новая сессия»: агент с блоком `coordinator` и окружение. Реплика в поле «Сообщение».
- Страница сессии: вкладка «Потоки» инспектора (`complementary "Инспектор сессии"`), таблица `Потоки`, строка потока субагента. Выбор потока фильтрует ленту и блок «Ожидает подтверждения» (`components/session/ToolConfirmationRequests.tsx`, отбор по потоку в `pages/SessionDetail.tsx`).
- Шапка сессии на пределе: заметка `[data-session-note="limit"]` с кнопкой «Поднять предел» (`components/session/SessionHeader.tsx`). Консоль предел не задаёт и чисел не показывает.
- Форма агента, «Изменить», вкладка «Мультиагентность»: список субагентов, флажок «Сам агент», флажок «Агенты, которых описывает сам агент», поле «Советник» (`#agent-advisor`), строка «Фоновые запуски» с пометкой «появятся позже».
- API: `POST /v1/sessions/:id/events` с `user.tool_confirmation` и необязательным `session_thread_id`; `_oma.limits` в создании, чтении и правке сессии; блок `multiagent_20261001` в `POST /v1/agents` (`platform/packages/managed-agents-api/API_LAYER.md`, разделы «Multiagent block», «Thread of a call answer», «Session limits»).

## Driving it with Playwright (verify-agent-console)

Preconditions:

- Прогон в режиме `fake`, `seed-user.sh` без `--others`. Сценарий: `scripts/journey.sh --run <RUN_ID> --scenario multiagent`.
- Порты прогона свободны. Сценарий проверяли на 8801, 8802 и 8803 (`VERIFY_PORT`, `VERIFY_FAKE_PORT`, `VERIFY_FAKE_MCP_PORT`).
- `sqlite3` есть на машине (его же требует `launch.sh`): журнал основного потока сессий с делегированием сценарий читает из базы прогона.

- **Исходные объекты (API).** Окружение «Без ограничений». Субагент `ma-checker-<n>` с `agent_toolset_20260401` и `configs: [{name: "bash", permission_policy: {type: "always_ask"}}]`. Основной агент `ma-coordinator-<n>` с `multiagent: {type: "coordinator", agents: [{type: "agent", id: <субагент>}]}`. Агент для предела `ma-limited-<n>` с набором по умолчанию. Строка «не проверено» `ma.seed_path`.
- **Делегирование.** «Сессии», «Новая сессия», `combobox` агента и окружения, `#session-title`, «Создать». В поле «Сообщение» строки `VERIFY_DELEGATE nonce=<n>c1`, `Агент: <id субагента>`, `Команда субагента: echo VERIFY_OK_<n>c1 >> /mnt/session/outputs/sub-<n>c1.txt; cat …`. Конец хода сценарий ждёт по `session.status_idle` в базе. `ma.subagent_waits`: поток из `GET /v1/sessions/:id/threads` с агентом субагента, в `GET /threads/:tid/events` bash с `evaluated_permission: ask` без результата и `session.thread_status_idle` с `requires_action` и `event_ids` `[id bash]`; у сессии те же `event_ids`; результат `call_agent_<id>` равен тексту ожидания; ответ `VERIFY_DELEGATE_WAITING_<n>c1`; файла `sub-<n>c1.txt` в `<прогон>/data/session-outputs/<tenant>/<сессия>/` нет. `ma.subagent_wrong_thread`: подтверждение с `session_thread_id: sthr_primary` даёт 400 с id потока вызова.
- **Счётчики.** `ma.limits_count` после первого хода и `ma.limits_grow` после «Разрешить»: `_oma.limits.used_tokens` равен 15 на каждый запрос к фейку с этим nonce (основной поток и субагент), `used_child_turns` равен числу `session.thread_status_running` потоков субагентов.
- **Страница.** Вкладка «Потоки», строка с именем субагента, блок «Ожидает подтверждения» с пунктом `bash`. Если блока нет живьём, свежая загрузка страницы и тот же поиск. Блок есть: клик «Разрешить», это и есть путь шага. Блока нет: `ma.ui_subagent_confirm` пишет провал с причиной, а «Разрешить» идёт по API с `session_thread_id` потока субагента.
- **Разрешить.** `ma.subagent_allow_once`: `user.tool_confirmation` с потоком субагента, ровно один `agent.tool_result` bash в потоке субагента с `VERIFY_OK_<n>c1`, фейк получил от субагента один запрос bash, в файле одна строка, у потока субагента `end_turn` и ответ `VERIFY_DONE_<n>c1`. `ma.subagent_report`: в основном потоке `agent.thread_message_received` от потока субагента с `VERIFY_DONE_<n>c1`, запрос основной модели с `decision: report_read` и `last_user_text` с `VERIFY_DONE_<n>c1`, ответ `VERIFY_DELEGATE_REPORT_<n>c1`, сессия `end_turn`.
- **Второе «Разрешить».** `POST /v1/sessions/:id/events` с тем же `tool_use_id` без `session_thread_id`. `ma.subagent_repeat_allow_none`: у принятого подтверждения поток субагента, после него нет `agent.message`, `span.model_request_start`, вызовов, результатов, `agent.thread_message_received`, `session.thread_status_running` и `session.error`, у фейка нет новых запросов, в файле одна строка.
- **Блок по API.** `ma.block_invalid`: 400 на агента со своим блоком в списке, на `inline_agents: disabled` при пустом списке и на советника без `model`. `ma.block_api`: агент `ma-block-<n>` с `subagents.predefined_agents: [<субагент>]` и `workflows.predefined_agents: [{type: "self"}]`; ответ создания равен `GET`, у обоих списков `inline_agents: {type: "enabled"}`, записи `{type: "agent", id, version}`, `self` стал id самого агента, советник `disabled`.
- **Форма блока.** Страница агента, «Изменить», окно «Изменение агента», вкладка `/^Мультиагентность/`. `ma.block_form`: на вкладке субагент списка, `checkbox "Сам агент"` снят, `checkbox "Агенты, которых описывает сам агент"` включён и доступен, есть `#agent-advisor` и «появятся позже»; снимки на 1280 и 390, на 390 нет прокрутки вбок; «Сохранить изменения» закрывает окно, блок в `GET /v1/agents/:id` тот же, что до формы. Исключение одно: запись самого агента в `workflows` форма шлёт как `{type: "self"}` (находка 2 ревью), и сервер закрепляет её новой версией агента. Сценарий сравнивает блоки, заменив такую запись на `self`, и отдельно проверяет, что её версия равна версии агента после правки.
- **Делегирование нового типа.** Сессия по API. `ma.block_session_copy`: `agent.multiagent.type` равен `multiagent_20261001`, в `subagents.predefined_agents` субагент целиком (id, имя, версия). `ma.block_delegation`: тот же путь с подтверждением по API, у основной модели те же инструменты `call_agent_*`, что у `coordinator`, и только субагент из `subagents`.
- **Предел.** Сессия по API с `_oma: {limits: {max_tokens: 1}}` (строка «не проверено» `ma.limit_seed_path`), реплика `VERIFY_AGENT_RUN nonce=<n>l1` из консоли. `ma.limit_stop`: новая сессия с `used_tokens: 0`, ход встал на `budget_reached` после `agent.tool_result`, после результата нет `span.model_request_start`, нет `session.error` и `session.status_rescheduled`, у фейка один запрос, `used_tokens` 15. `ma.limit_refuses_message`: `user.message` по API даёт 400 с `_oma.limits` и `user.tool_confirmation` в тексте. `ma.limit_ui_note`: текст заметки ровно «Предел работы сессии исчерпан, агент остановился.» и кнопка «Поднять предел», цифр в заметке нет, в шапке нет слов расхода, на 390 заметка и кнопка видны без прокрутки вбок. `ma.limit_ui_send_refused`: кнопка отправки даёт уведомление «Предел работы сессии исчерпан. Сначала поднимите предел.», событий не прибавилось.
- **Подъём.** Кнопка «Поднять предел». `ma.limit_raise`: уведомление «Предел поднят», `max_tokens` и `max_child_turns` стали `2 × max(предел, израсходовано)`, ход без новой реплики кончился `end_turn` с `VERIFY_DONE_<n>l1`, bash и его результат по одному, у фейка два запроса, в файле одна строка, заметки нет.
- **Доказательство.** `summary.md`, `api/ma-10-…` (журнал из базы, потоки, журнал потока, сессия, счётчики, отказ чужого потока), `api/ma-11-coordinator-events-list-response.json` (ответ `GET /events`), `api/ma-12-…`, `api/ma-13-…`, `api/ma-2x-…` (блок), `api/ma-3x-…` (предел), `logs/fake-model-requests.jsonl`, снимки `ma-coordinator-page-live`, `ma-coordinator-page-reload`, `ma-block-form-1280`, `ma-block-form-390`, `ma-block-form-390-bottom`, `ma-limit-note-1280`, `ma-limit-note-390`, `ma-limit-raised`.

## Gotchas

- Находка 5 ревью шага 1 (2026-10-18). Pi сам пишет `agent.thread_message_sent` с `to_thread_id` на каждый `call_agent_*` (`apps/agent/src/harness/tool-events.ts`). Схема ответа его не принимает: `GET /v1/sessions/:id/events` отвечает 500 «invalid session event page», а поток `/events/stream` обрывается событием `error` на этом же событии. Живая страница после реплики застревает на «Выполняется» и «Агент работает…», поток субагента в «Потоках» не появляется. После свежей загрузки поток есть, но лента пустая («Отправьте сообщение, чтобы начать сессию.»), и блока «Разрешить» в потоке субагента нет. Поэтому `ma.ui_subagent_confirm` пока провал, а журнал основного потока сценарий читает из `managed_session_events` базы прогона (`sqlite3 -readonly`, документы во внутреннем виде camelCase). Журнал потока субагента `GET /threads/:tid/events` отдаёт без ошибки. Убрать это событие должен срез 2 шага 3.3 плана; после этого проверка станет зелёной сама, и «Разрешить» пойдёт кликом.
- `GET /v1/sessions/:id/threads` не отдаёт основной поток, только потоки субагентов, как CMA. `GET /threads/sthr_primary/events` отвечает 404.
- Решения фейка: маркер `VERIFY_DELEGATE nonce=<n>` со строками `Агент:` и `Команда субагента:` (`decideDelegate` в `scripts/fake-model.mjs`). Субагент получает `VERIFY_AGENT_RUN nonce=<n>` и идёт общей веткой. Любое сообщение пользователя после реплики с маркером фейк считает отчётом субагента: лишняя реплика в той же сессии даёт `VERIFY_DELEGATE_REPORT_NOT_OK`.
- Пока субагент ждёт человека, сервер принимает `user.message` и запускает ход основного агента. Сценарий таких реплик не шлёт.
- Предел по умолчанию задают `OMA_SESSION_MAX_TOKENS` и `OMA_SESSION_MAX_CHILD_TURNS` (1 000 000 и 20). Консоль предел не задаёт, поэтому сессия с `max_tokens: 1` создаётся по API.
- Кнопка «Поднять предел» удваивает большее из предела и израсходованного: при `max_tokens: 1` и 15 токенах первого запроса новый предел 30. Второй запрос доводит счёт до 30, ход кончается `end_turn`, нового упора нет.
