# Хранилища секретов и MCP

Хранилище секретов держит учётные данные. Есть два вида:
- учётные данные MCP-сервера: OAuth или Bearer-токен, привязаны к URL сервера;
- учётные данные CLI.

Агент получает MCP-серверы на вкладке «MCP-серверы». Хранилище подключается к сессии в окне «Новая сессия».
Когда агент обращается к MCP-серверу, сервер платформы подставляет токен из хранилища, найденного по URL. Сам токен в агента и в песочницу не попадает.

## Sub-features

- `vault-create` — окно «Новое хранилище», поле «Название».
- `vault-mcp-credential` — «Добавить» → окно «Добавить учётные данные», вкладка «MCP-сервер», тип «Bearer-токен» или «OAuth».
- `vault-cli-credential` — та же форма, вкладка «CLI»: `#vault-cli-id`, `#vault-cli-display-name`, `#vault-cli-token`.
- `vault-credential-edit` — кнопки «Изменить: {имя}» и «Удалить: {имя}» в строке учётных данных.
- `agent-mcp` — вкладка «MCP-серверы» в форме агента: «Выбрать из списка» или «Свой сервер» (`#mcp-name-{i}`, `#mcp-type-{i}`, `#mcp-url-{i}`).
- `session-vault` — флажок хранилища по `display_name` в окне «Новая сессия».
- `mcp-call-with-vault` — вызов MCP-инструмента в ходе агента, токен подставляется из хранилища.

## How to get to it (user POV)

- Боковое меню, ссылка «Хранилища секретов» (`g` `v`), маршрут `/vaults`, кнопка «Новое хранилище». Клик по строке открывает `/vaults/:id`.
- На карточке хранилища кнопка «Добавить» в разделе учётных данных.
- Форма агента, вкладка «MCP-серверы».
- Окно «Новая сессия»: флажки хранилищ. Они видны, только если хранилища есть.

## Driving it with Playwright (verify-agent-console)

Preconditions:

- Учётка вошла в консоль, хранилищ нет.
- Для `mcp-call-with-vault` нужен локальный MCP-сервер, который проверяет `Authorization: Bearer <тестовый токен>`. В скилле его **пока нет**, поэтому этот пункт сейчас «не проверено». Заглушку стоит добавить по образцу `scripts/fake-model.mjs` на свободном порту, например 8793.
- Скрипта для этой функции нет. Шаги выполняются кодом Playwright по образцу `scripts/journey-env-to-agent.mjs`.

- **Создать хранилище.** Нажать ссылку «Хранилища секретов», затем `getByRole("button", { name: "Новое хранилище" }).first()`. В `getByRole("dialog", { name: "Новое хранилище" })` заполнить `#vault-name` значением `verify-vault-<n>` и нажать «Создать». Результат: строка в списке. `GET /v1/vaults` содержит хранилище с `display_name`.
- **Добавить Bearer для MCP.** На `/vaults/:id` нажать «Добавить». В `getByRole("dialog", { name: "Добавить учётные данные" })`:
  - заполнить `#vault-mcp-name`;
  - в группе «Тип» нажать «Bearer-токен» (`aria-pressed`);
  - в `#vault-mcp-server` ввести `http://127.0.0.1:8793/mcp`;
  - раскрыть «Токен доступа» и ввести тестовый токен `verify-token-<n>`;
  - нажать «Добавить».

  Результат: в `[data-testid="credential-list-surface"]` строка с кнопками «Изменить: …» и «Удалить: …». `GET /v1/vaults/:id/credentials` возвращает `auth.type = "static_bearer"` и `auth.mcp_server_url`. Поля `token` в ответе нет (`packages/managed-agents-api/src/contracts/credentials.ts:170-175`).
- **MCP-сервер у агента.** В форме агента открыть вкладку `getByRole("tab", { name: /^MCP-серверы/ })` и нажать «Свой сервер». Заполнить `#mcp-name-0`, `#mcp-type-0` (url) и `#mcp-url-0` (тот же URL). Результат: в YAML агента есть `mcp_servers` с этим URL.
- **Хранилище в сессии.** В окне «Новая сессия» отметить флажок с подписью `verify-vault-<n>`. Результат: `GET /v1/sessions/:id` возвращает `vault_ids` с id хранилища, в шапке сессии бейдж `[title="Хранилище секретов: verify-vault-<n>"]`.
- **Вызов MCP.** Фейковая модель (её нужно расширить) вызывает MCP-инструмент заглушки. Ожидается: в журнале `agent.mcp_tool_use` и `agent.mcp_tool_result`, а в логе заглушки заголовок `Authorization: Bearer verify-token-<n>`. Токен приходит из хранилища (`apps/main-node/src/modules/node-managed.ts:127-160`, совпадение по `mcp_server_url`). Сейчас «не проверено».
- **Доказательство.** Скриншоты карточки хранилища и окна учётных данных, `api/vault.json`, `api/vault-credentials.json` (без токена), `api/session-with-vault.json`, лог заглушки MCP.

## Gotchas

- Учётные данные CLI на main-node в песочницу не подставляются. Резолвер собран, но не подключён: `void _capResolver` в `apps/main-node/src/modules/node-http.ts:945-964`, комментарий «future Node outbound proxy». Не засчитывайте CLI-учётку как работающую по одному факту создания.
- `apps/oma-vault` в эту копию не перенесён (`docs/runbook-local.md`, ограничение 5). Подстановка секретов в исходящий трафик песочницы через `OMA_VAULT_PROXY_URL` недоступна.
- Токен подставляется, только если URL MCP-сервера агента точно равен `mcp_server_url` учётных данных. Слеш в конце или другой хост дают «нет учётных данных».
- В окне «Добавить учётные данные» поле «Токен доступа» спрятано в свёрнутом блоке. Кнопка отправки называется «Подключить», пока нет токена и не выбран Bearer, после этого — «Добавить».
- На окружении с сетью «Ограниченный» и выключенным «Разрешить сетевой доступ MCP-серверам» вызовы MCP блокируются. Ограничение действует на MCP, но не на bash в VM.
- Маршруты `/v1/vaults*` требуют beta `managed-agents-2026-04-01`.
