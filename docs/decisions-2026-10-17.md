# Решения 2026-10-17

Продолжение [decisions.md](decisions.md). Оба решения принял владелец 2026-10-17. Если текст [design.md](design.md), спек [components/](components/) или планов [plans/](plans/) с ними расходится, верно то, что написано здесь.

## D41. Остался только harness Pi

**Контекст.** В платформе было четыре harness: встроенный цикл Pi, `acp-sandbox` (Claude Code, Codex, Gemini, OpenCode, Kimi и pi-acp внутри VM LiteBox), `acp-proxy` (агент на ноутбуке через мост) и устаревший `ai-sdk` (`DefaultHarness`). Рабочую модель Qwen ведёт только Pi. ACP-агенты ни разу не работали с настоящей моделью: сценарий `claude-code` скилла `verify-agent-console` проходил только на фейковой модели, режим `real` не запускался. `acp-proxy` на Node не работал, ему нужна серверная часть моста для Cloudflare. Разбор 2026-10-17 ([plans/harness-fixes.md](plans/harness-fixes.md)) нашёл пять дефектов в наших обёртках ACP и `ai-sdk`, а не в самих агентах.

**Решение.**

1. Ход ведёт только Pi. Имена `default` и `pi` дают один и тот же `PiHarness`.
2. Удалены `acp-sandbox`, `acp-proxy`, `ai-sdk`, карточки harness, прокси модели для VM (токены `oma_sbx_`, вид учётных данных `sandbox_inference`), страницы консоли «Harness» и «Локальные среды», выбор harness в форме агента и инструменты карточек harness у помощника. Пакеты, которые служили только ACP и мосту, перечислены в [platform/ORIGIN.md](../platform/ORIGIN.md).
3. Сохранённый агент со старым harness (`ai-sdk`, `acp-sandbox`, `acp-proxy`) работает на Pi. Сервер пишет одно предупреждение на имя.
4. Создание и правка агента с другим harness или с блоком `acp` получают отказ «Остался только встроенный цикл. Уберите harness и блок acp.». Чтение старых агентов не падает, поля `acp` и `runtime_binding` в сохранённых документах сервер пропускает.
5. Уже записанные спаны `acp_prompt` консоль показывает. Новых спанов ACP проектор трейса не пишет.
6. Таблица `harness_cards` остаётся в старых базах. Миграции удаления нет.
7. Остаются Pi, карточки моделей, окружения, образы песочницы, LiteBox, `spawnDuplexProcess` порта песочницы и `@openma/common`.

**Почему.** Дефекты сидели в нашей обёртке, а не в агентах. ACP с настоящей моделью никто не запускал. Каждый лишний harness требует своих тестов, прокси, guard и страниц консоли. Владелец решил держать один цикл.

**Как вернуть.** Код до удаления лежит в коммите `1d1a43b`.

## D42. Temporal отложен

**Контекст.** [design.md](design.md) и спека [02](components/02-session-workflow.md) ведут сессию через Temporal. Сервер сейчас работает иначе: очередь в SQL, `NodeSessionExecutionWorker` берёт ход с арендой на 30 с, события хода пишутся по fence аренды (`platform/AGENTS.md`, раздел «Ход агента на сервере»). Свой сервер Temporal или Temporal Cloud требует отдельной машины и человека, который ведёт версии workflow (D23).

**Решение.** Temporal пока не вводим. Возвращаемся к нему, если выполнено хоть одно условие:

1. Появились бизнес-процессы поверх сессий, которые ждут днями.
2. Тест на двух репликах с `kill -9` падает, и местные правки его не чинят.
3. Сервер работает на нескольких машинах, и очередь стала настоящим узким местом.
4. Есть отдельный сервер Temporal или Temporal Cloud и владелец версий workflow.

**Ближайший план вместо Temporal.**

1. Postgres вместо SQLite. Сначала починить ошибку `42P18` при захвате исполнения ([runbook-local.md](runbook-local.md)).
2. Тест на двух репликах: две копии `main-node` на одной базе Postgres, одну убивают `kill -9` посреди хода, ход доводит вторая.
3. Проход по зависшим исполнениям возвращает сессию в `idle`, если её ход потерял воркер.
4. Тик расписания деплойментов берёт блокировку в SQL, чтобы две реплики не запустили один прогон дважды.
5. Файлы и снимки песочницы в S3, восстановление песочницы через `checkpoint_restore`.

**Почему.** Очередь с арендой уже отдаёт ход другому воркеру, когда аренда истекла. Пять шагов плана проверяют это на двух репликах без новой системы. Условия выше показывают, когда этого станет мало.
