- **Один владелец файла.** В волне у файла ровно одна единица. Передача файла только между волнами, после коммита, по таблице 5.3.
- **Чужие потоки.** Сейчас идут три потока, их файлы берутся только с волны 2, после их коммита:
  - RS, правки сессии, оболочки и сервера (по `git status` на 2026-10-16): `CanonicalSessionTurn.tsx`, `SessionDetail.tsx`, `AgentFormDialog.tsx` и тест, `ConsoleShell.tsx`, `ConsoleSurface.tsx`, `SessionsList.tsx`, `Markdown.tsx`, `ai-elements/tool.tsx`, `session/format-ru.ts`, `index.css`, `styles/console-list.css`, `console-shell.css`, `ddc-tokens.css`, `ddc-wiring.test.ts`, `DataTable.phone.test.tsx`, новые `lib/tool-output.ts`, `lib/optimistic-user-message.ts`, `SessionDetail.prompt.test.tsx`, `SessionsList.test.tsx`; на сервере `N/modules/node-http.ts`, `node-managed.ts`, `node-foundation.ts`, `N/config.ts`, `N/lib/node-managed-session-runtime.ts`, `node-managed-workspace-checkpoints.ts`, пакеты сессий и песочницы;

  - CC, Claude Code в песочнице ([runbook-claude-code-sandbox.md](../runbook-claude-code-sandbox.md)): все файлы `S/`, `platform/apps/agent/src/harness/acp-translate.ts`, `P/sandbox*`.

  Перед стартом единица делает `git status --short <свои файлы>`. Есть чужие правки, значит ждёт.
- **Галерея волны 1.** Пока меню и маршруты заняты, общие компоненты видны на странице `ui-gallery.html` в режиме разработки Vite (Vite отдаёт любой `.html` из корня приложения без правки `vite.config.ts`). K0 заводит `platform/apps/console/ui-gallery.html` и `C/ui-gallery/main.tsx`, который собирает разделы `C/ui-gallery/sections/*.tsx` через `import.meta.glob`. Каждая единица волны 1 добавляет свой файл раздела. Порт разработки не 5173 и не 5174 (они чужие), например `vite --port 5180`.
- **Маршруты.** K0 пишет реестр `C/routes/registry.ts`: он собирает `C/pages/**/route.tsx` через `import.meta.glob`. В `main.tsx` его подключает K8 в волне 2. Дальше новая страница добавляет свой `route.tsx` и `main.tsx` не правит. Пункт меню виден, только если его маршрут есть в реестре или в `main.tsx`.
- **Стили.** В волне 1 новых CSS-файлов нет: Tailwind на шкалах DDC и классы DDC (`.card`, `.kpi`, `.segmented`, `.chip`, `.menu`, `.callout`). Стили меню и колонки 48 px K8 пишет в `console-shell.css` в волне 2.
- **Тексты.** `C/i18n/*` правит только K0. Остальные единицы держат строки в своих `*-text.ts`, как C1 с `harness-text.ts`.
- **Миграции.** Новые таблицы аналитики и наблюдаемости создаёт код при первом обращении, как в analytics.md (раздел 4.1). Drizzle-миграции только у таблиц upstream: `api_keys` (S7) и при нужде индекс запусков деплоймента (S6). В волне не больше одной единицы с миграцией, номер следующий свободный (сейчас последний `0027`).
- **Контракты.** Консоль пишет по контрактам раздела 4.6, плана моделей и analytics.md и проверяет их на подставных ответах (`msw`). Живая сверка в скилле, когда сервер подключён.
- **Проверка единицы.** Сначала падающий тест. Тесты и сборка только через `test-slot` (`test-slot pnpm test`, `test-slot pnpm typecheck` в `platform/apps/console` или `platform/apps/main-node`), без watch. Скриншоты 1280 и 390 px без горизонтальной прокрутки в описании коммита. Тексты проходят `node scripts/unslop-check.mjs --diff`.
- **Ноутбук.** Одновременно не больше 5 агентов, тяжёлые команды через `nice`, скилл гоняется одним прогоном.

### 4.6 Новые серверные контракты

Все под `/v1/oma`, кроме второго пути S8. Доступ как у остальных `/v1/oma/*`. Ошибки в формате managed API, тексты по-русски. S1, S2 и подключение описаны в плане моделей, аналитика в analytics.md.

- **S3r. Расход за всю сессию.** `session.usage` копится за все ходы сессии, а не за последний (`N/lib/node-managed-harness-runtime.ts`, создание `createNodeHarnessUsageLedger`). Это остаток S3, который analytics.md вынес за свой контракт.
- **S4. Создатель записи.** Промежуточный обработчик на создание агента, сессии, окружения, хранилища секретов, хранилища памяти, деплоймента пишет `metadata.oma_created_by = "user:<id>"` или `"key:<id ключа>"`. Значение клиента заменяется. На изменении поле не меняется, даже если клиент его прислал. Формы агента и окружения поле скрывают и сохраняют. Имена берутся из участников пространства.
- **S5. Наблюдаемость агента.** Таблицы `session_facts` (сессия, агент, версия, статус, ходы, `active_seconds`, ошибка, результат, причина остановки) и `tool_calls` (сессия, агент, инструмент, ошибка, длительность) создаёт код (`ensureObservabilitySchema`, свой журнал шагов), как в analytics.md. Пишет обёртка `withSessionFactRecording` над runner по кадрам хода. Ошибка сессии это событие `session.error` или статус `terminated`. Маршрут `GET /v1/oma/analytics/agents/:id/overview?from&to&version&group_by=version|outcome|error&bucket=hour|day`: сессии, доля ошибок, токены (из `model_calls`), p50, p90, p95 ходов, активного времени и токенов на сессию, ряды сессий по корзинам и группе, инструменты (вызовы, ошибки), причины остановки, `latest_ended_at`. Монтируется отдельным роутером на `/oma/analytics/agents`.
- **S6. Исполнитель расписаний.** Задача `deployment-tick` раз в минуту: активные деплойменты с наступившим сроком, `beginScheduled` в `deployment-run-store`, запуск с `trigger_type = scheduled`, сессия, `last_run_at`, `upcoming_runs_at`. Две реплики на одну минуту не дают второго запуска (уникальный индекс запуска на минуту, миграция при нужде).
- **S7. Ключи API.** Миграция: `expires_at`, `disabled_at` в `api_keys`. В списке `user_id`, `last_used_at`, `expires_at`, `status` (`active`, `disabled`, `expired`). `POST /api_keys` принимает `expires_at`. `POST /api_keys/:id/disable`, `/enable`. Отключённый или истёкший ключ получает 401 (проверка в `findByHash`). `last_used_at` пишется не чаще раза в минуту.
- **S8. Прямой вызов модели.** `POST /v1/oma/messages` и тот же обработчик на `POST /v1/messages`, чтобы SDK с `base_url` нашего сервера работал из фрагментов Площадки. Тело как у Messages API, подмножество: `model` это handle из `model_options`, `system`, `messages` с текстом, картинками и документами (в том числе `source.type = file` с `file_id` из `/v1/files`), `max_tokens`, `temperature`, `stop_sequences`, `stream`, `thinking`, `output_config.effort`, `tools` только custom, `tool_choice`, `output_format`. Ответ JSON или SSE (`message_start`, `content_block_*`, `message_delta`, `message_stop`) и заголовок `x-oma-model-call-id`. Модель вызывается через Pi по карточке (ключ и `wire_model` на сервере), встроенная через ключ сервера. Строка журнала пишется через переданный приёмник в хранилище AN: `harness = "direct"`, пустые `session_id` и `agent_id`, `agent_name = "Площадка"`. Ключ окружения (`oma_env_`) получает 403. Тело до 1 МБ, таймаут 10 мин.
- **S9. Лимит загрузки.** `UPLOAD_MAX_BYTES` в `N/config.ts` (по умолчанию 25 МБ). `POST /v1/files`, `POST /v1/skills`, `POST /v1/oma/skills` сверх лимита дают 413 «Файл больше N МБ» до чтения тела целиком.

## 6. Волны и время

Время это часы работы агентов при 5 одновременно, без ожидания чужих коммитов и ответов владельца. Каждая волна кончается коммитом, `graphify update .`, прогоном скилла (с волны 2) и скриншотами владельцу.

| Волна | Параллельно | Условие старта | Время |
|---|---|---|---|
| 1. Каркас | K0, K1, K2, K3, K4, S1, S2, S3r, S4, S8 (два захода по 5) | сейчас, только свободные файлы | 6-8 ч |
| 2. Сессия и подключение | K8, C1, K5, K5b, K5c, K6, K7, SW, S5, S6, VP2 (K5 после C1, VP2 заканчивает последней) | коммит волны 1, RS, AN, CC | 10-12 ч |
| 3. Агент, списки, аналитика, Claude Code | K9, K10, K11a, K11b, K12, K13, S7, SX, V1 + VP3 (K9 после K10, K12 после K9, SX после S5 и S6) | коммит волны 2 | 10-12 ч |
| 4. Сборка и управление | K14, K15, K16, K17, K18, S9, VP4 (K18 после K17) | коммит волны 3 | 8-10 ч |

Итого 34-42 ч, около 5 рабочих дней. Самый длинный путь: K1 → K6 → K10 → K9 → K12 → V1 + VP3 → K14 → VP4.

## 10. Риски

- Чужие потоки RS, AN и CC не закоммичены вовремя: волна 2 сдвигается целиком, волна 1 от них не зависит.
- Два инспектора (`RowInspector` AN и `Inspector` K2) и две копии копирования ID и мультивыбора живут до отдельной чистки. Поведение у них одно (analytics.md 6.2), вид проверяется скриншотами.
- K3 и K18 опираются на компоненты AN. Если AN поменяет их интерфейс до коммита, K3 правит только свои вызовы.
- Пакеты стоят на запусках оценки: задача `eval-tick` на Node есть, но сквозной прогон не делался. Если он не работает, к волне 4 нужна серверная единица исправления.
- `POST /v1/messages` на нашем сервере совпадает с путём Anthropic. Клиент, настроенный на наш `base_url` по ошибке, потратит деньги карточки. Ключи окружений закрыты.
- Строки Площадки в `model_calls` с пустыми `session_id` и `agent_id` попадут в фасеты AN как пустой агент. K13 подписывает их, фильтр по агенту проверить в VP4.
- Пики по минутам считаются по концу вызова, для Claude Code одна строка на ход: пик грубее. Это в подсказке AN.
- Доля чтения кэша и стоимость зависят от того, как провайдер и `claude-agent-acp` считают `input_tokens` (план моделей, раздел 6).
- Реестр маршрутов через `import.meta.glob` меняет подключение страниц, тест реестра в K0 обязателен.
- Галерея `ui-gallery.html` есть только в режиме разработки и в сборку не попадает. Проверки волны 1 в браузере идут на ней, в скилле с волны 2.
