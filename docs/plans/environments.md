## 0. Коротко

1. Агент может ставить пакеты сам, потому что VM работает от root, а у «Песочницы по умолчанию» сеть открыта. Мешают три вещи. Образ `node:22-bookworm` (`P/sandbox-adapter-litebox/src/litebox.ts:75, 485`) не содержит pip, офисных библиотек и шрифтов. Агенту никто не говорит, где он работает и что ему можно. Правило «после трёх одинаковых сбоев отчитайся и закончи ход» (`A/harness/platform-guidance.ts:14-15`) модель читает как «остановись».
2. Решение из шести частей:
   - образ «Рабочее место агента» с Python в venv, офисными библиотеками, библиотеками данных и шрифтами с кириллицей, плюс вариант с LibreOffice. Окружение выбирает образ ключом каталога, VM запоминает дайджест образа;
   - пакеты окружения платформа готовит в отдельной сборочной VM без секретов и файлов сессии, закрепляет версии и хеши и ставит в рабочую VM без сети;
   - четыре шаблона окружений при создании;
   - блок «Окружение» в системном промпте. Его текст строится по снимку конфигурации, которую получила именно эта VM, и по тому, где на деле работает агент;
   - закрепление пакета, поставленного в сессии, в окружении по кнопке пользователя;
   - навык только объявляет зависимости. Решает окружение, недостающий пакет пользователь добавляет в окружение кнопкой.
3. Граница доверия это VM. Код в VM, свой или из пакетов, считается кодом агента. План не защищает VM от её же кода. Он ограничивает то, что в VM лежит, и то, куда VM может слать данные (раздел 3).
4. Веб-поиск выбирает провайдера по настройке сервера. В сети «Ограниченный» поиск выключен, пока окружение его явно не разрешит, потому что текст запроса уходит провайдеру. Для закрытого контура провайдер это свой SearXNG.
5. В verify-agent-console 22 жёсткие проверки, среди них отказы сети, утечки фиктивных секретов и рендер кириллицы картинкой. Решение модели поставить пакет доказывает только живой прогон EQ1.
6. Три волны, около 4 дней работы агентов. Образ и чистые функции делает Codex, сервер Opus, консоль Sonnet.

### 0.1 Что можно сделать сегодня без кода

- Поток document-skills уже даёт такой путь шаблоном «Документы» (`C/lib/environment-templates.ts`): apt `python3-pip fonts-dejavu-core` и офисные pip-пакеты.
- В «Песочнице по умолчанию» добавить apt-пакеты `python3-pip python3-bs4 python3-lxml python-is-python3`. apt ставится первым (`P/sandbox/src/environment-setup.ts:54`), поэтому после этого заработают и pip-пакеты окружения. Цена: `apt-get update` и установка при каждом старте VM, оценка 20-40 с.
- Серверу задать `LITEBOX_DISK_SIZE_GB=4`. Без него на диске VM свободно около 120 МБ (`litebox.ts:80-83`).
- Не добавлять pip-пакеты без `python3-pip` в apt. Скрипт выйдет с кодом 127, VM остановится, и ни одна сессия окружения не стартует (`environment-setup.ts:105-111, 127-129`, `litebox.ts:556-571`).
- Дописать в системный промпт агента строку: «You are root in Debian 12. If a Python module is missing, run apt-get install -y python3-<name> or pip install --break-system-packages <name>, then continue».

Всё это ставит пакеты прямо в рабочей VM рядом с файлами сессии. Риски такого пути описаны в разделах 3.5 и 3.8, до кода плана их нечем закрыть. В VM это не проверялось. Проверка одним ходом bash: `python3 -m pip --version; ls /usr/lib/python3*/EXTERNALLY-MANAGED; df -h / | tail -1`.

## 1. Образ «Рабочее место агента»

### 1.1 Что сейчас

- Образ один на сервер, переменная `SANDBOX_IMAGE` (`litebox.ts:900`). У окружения поля образа нет (`P/managed-agents-domain/src/environments/environment.ts:19-25`).
- VM создаётся на сессию, пакеты окружения ставятся при каждом старте VM. Кэша пакетов между сессиями нет, у Claude он есть.
- Команды агента идут через `sh -c` (`litebox.ts:187`), в Debian это dash. Инструмент называется bash, и `[[ ]]`, `source`, `set -o pipefail` в нём ломаются.
- Диск VM по размеру образа, свободно около 120 МБ. Память по умолчанию 512 МиБ, 1 CPU.
- Образ Cloudflare-версии `openma/sandbox-base` (`platform/apps/agent/Dockerfile:1-66`) богаче, но в нём тоже нет bs4, python-pptx и LibreOffice. Он собран на `cloudflare/sandbox` со своим ENTRYPOINT, работу в BoxLite никто не проверял. Поэтому собираем свой.
- У Claude в облачной песочнице уже есть python-pptx, python-docx, openpyxl, pypdf, pandoc, LibreOffice, шрифты и навыки pptx, xlsx, docx, pdf. Презентации там работают без настройки.

### 1.3 Размер, ресурсы и пределы

| Образ | Предел на диске | Ресурсы VM в каталоге на старте |
|---|---|---|
| `legacy`, `node:22-bookworm` | 1,3 ГБ, замер (`litebox.ts:81`) | 512 МиБ, 1 CPU, диск 4 ГБ |
| `workplace` | не больше 2,0 ГБ, оценка около 1,8 ГБ | 1024 МиБ, 2 CPU, диск 6 ГБ |
| `workplace-office` | не больше 2,6 ГБ, оценка около 2,2 ГБ | 2048 МиБ, 2 CPU, диск 8 ГБ |

Пределы и кто их проверяет:

- Размер каталога OCI. `build.sh` падает, если `du -sb` больше предела из таблицы.
- Память VM. EX1 меряет пик памяти в VM на `render-ru.py` и на типовых задачах: python-pptx на 20 слайдов, pandas на 100 тыс. строк, `soffice --convert-to pdf`. Если пик больше 70% памяти из каталога, EX1 поднимает число в `catalog.json` и пишет замер в README.
- Готовность VM, от создания до первого успешного exec без пакетов окружения. Холодный старт `workplace` (образ на хосте ещё не запускался) не дольше 30 с, тёплый не дольше 5 с, тёплый `workplace-office` не дольше 8 с. EX1 меряет по 5 раз и три VM одновременно, EV1 проверяет тёплый старт (`env.ready_time`). Подтверждённые 2-3 с (`S/features/environments.md:70`) относятся к старому образу с тёплым кэшем, для новых образов чисел нет.
- Подготовка слоя пакетов (3.3). Таймаут 600 с, слой не больше 1024 МБ (`SANDBOX_LAYER_MAX_MB`), одновременно не больше одной подготовки (`SANDBOX_MAX_PREPARES=1`).
- Установка слоя в рабочую VM (3.4). Таймаут 120 с.
- Одновременные VM на хосте. `SANDBOX_MAX_VMS` (по умолчанию 4) и `SANDBOX_MEMORY_BUDGET_MIB` (по умолчанию половина памяти хоста). Сборочная VM тоже считается. VM сверх предела ждёт до 60 с, потом ход падает с ошибкой `sandbox_capacity`.
- Тяжёлые пакеты больше не ставятся в каждой сессии. Слой готовится один раз на набор пакетов, следующие сессии ставят его без сети (3.3, 3.4).

Старые окружения на новый образ сами не переходят. В `catalog.json` `default_image` остаётся `legacy`, и окружения с `config.image = null` живут на прежнем образе. Переход делает EX4 после замеров EX1 и `env.ready_time` в EV1 и только с согласия владельца.

### 1.4 Файлы и сборка

Файлы в `I/`:

- `Dockerfile` с двумя целями: `workplace` и `office` (`FROM workplace` в том же файле, чтобы buildx не искал базу в реестре);
- `requirements-workplace.txt` с закреплёнными версиями;
- `manifest.sh` пишет `/etc/oma/image-manifest.json` при сборке и умеет снять манифест с чужого образа (для `legacy`);
- `build.sh <цель> <версия>` собирает каталог OCI, пишет манифест и дайджест;
- `smoke.sh <тег>` проверяет образ в `docker run`;
- `scan-secrets.sh <тег>` ищет в конфигурации, манифесте и `docker history --no-trunc` адреса с логином и токены (3.7);
- `selftest/render-ru.py` и `selftest/sample-ru.txt`;
- `boxlite-smoke.mjs <каталог>` поднимает VM BoxLite из каталога и меряет старт. `@boxlite-ai/boxlite` он берёт через `createRequire` от `P/sandbox-adapter-litebox`, новых зависимостей нет;
- `catalog.json` и `README.md`.

Сборка на машине разработчика:

```sh
cd platform/sandbox-images
export SANDBOX_IMAGE_DIR=~/.cache/ai-backoffice-v3/environments/sandbox-images
docker buildx create --name oma-images --driver docker-container --use   # один раз
nice -n 15 ./build.sh workplace 2026.10.1
nice -n 15 ./build.sh office 2026.10.1
```

`build.sh` внутри:

```sh
# 1. ждёт, пока sensors покажет не выше 92°C и свободной памяти не меньше 3 ГБ
# 2. отказывает, если $SANDBOX_IMAGE_DIR/$NAME-$VERSION уже есть
# 3. отказывает, если адрес зеркала в аргументах содержит user@, ? или #
docker buildx build --platform linux/amd64 --target "$TARGET" \
  --output "type=oci,dest=$SANDBOX_IMAGE_DIR/$NAME-$VERSION,tar=false" .
docker buildx build --platform linux/amd64 --target "$TARGET" --load -t "oma/$NAME:$VERSION" .
docker run --rm "oma/$NAME:$VERSION" cat /etc/oma/image-manifest.json \
  | jq --arg d "$(jq -r '.manifests[0].digest' "$SANDBOX_IMAGE_DIR/$NAME-$VERSION/index.json")" \
       '. + {image_digest: $d}' > "$SANDBOX_IMAGE_DIR/$NAME-$VERSION.manifest.json"
# 4. падает, если du -sb каталога больше предела из 1.3
```

Драйвер `docker` пишет формат OCI только с containerd image store, поэтому отдельный builder с драйвером `docker-container`. На машине стоят Docker 29.8.2 и buildx 0.37.2, skopeo и podman нет. Сборки идут по одной.

`selftest/render-ru.py` проверяет кириллицу по картинке, а не по тексту PDF. Для каждого формата он берёт короткий русский образец: панграмму с «ё», «й», «щ», заголовок и абзац длиннее строки.

- docx через python-docx со шрифтами Calibri и Times New Roman, xlsx через openpyxl с Arial, pptx через python-pptx с Calibri. Все три переводит в PDF `soffice --headless --convert-to pdf`.
- PDF через reportlab с зарегистрированным `DejaVuSans` из `/usr/share/fonts/truetype/dejavu/`.
- Каждый PDF переводит в PNG `pdftoppm -r 150`, затем распознаёт `tesseract -l rus`.
- Проходит, если распознаны не меньше 95% слов образца; `pdffonts` показывает встроенные Carlito, Liberation или DejaVu и не показывает Type 3; длинный абзац занимает больше одной строки в `pdftotext -layout` и не выходит за поле страницы.
- Контроль: тот же PDF reportlab со шрифтом по умолчанию Helvetica даёт меньше 50% слов. Так видно, что проверка ловит пустые квадраты.

Как образ попадает в BoxLite. BoxLite не читает образы локального docker, он качает их из реестра. У `SimpleBox` есть `rootfsPath`, каталог в формате OCI layout, он заменяет `image` (`simplebox.d.ts:74-75` в `@boxlite-ai/boxlite` 0.9.0). Адаптер сейчас передаёт только `image` (`litebox.ts:490-498`). Правка ES2 передаёт `rootfsPath`, диск, память и CPU из каталога.

Что BoxLite 0.9.0 поднимет VM из каталога buildx с `tar=false`, никто не проверял. Это первая приёмка EX1 через `boxlite-smoke.mjs`. Если `rootfsPath` не работает, EX1 публикует образ в реестр (GHCR для разработки), пишет в каталог ссылку с дайджестом и поднимает VM этим путём. Запись в README без работающей VM приёмкой не считается. Внутренний реестр с http или логином требует `imageRegistries` рантайма BoxLite (`native-contracts.d.ts:87-102`), это отдельная правка позже.

На машине разработчика и в проверке это `~/.cache/ai-backoffice-v3/environments/sandbox-images`. Без каталога сервер работает как сейчас: одна запись `default` из `SANDBOX_IMAGE`.
- Запись, у которой каталога на диске нет или дайджест не сходится (1.6), сервер помечает `built: false` с причиной. Сессия на таком образе получает ошибку с именем образа, тихой подмены на другой образ нет.
- Окружение получает поле `config.image` с ключом каталога. Значение `null` значит `default_image` в момент создания VM. Это наше расширение API, у Claude такого поля нет. Неизвестный ключ отклоняет порт политики окружения ответом 400 (ES1). `config` хранится JSON (`P/environments-store/src/adapters/sql-environment-repo.ts:46`), миграция не нужна.
- `GET /v1/oma/sandbox-catalog` отдаёт образы (ключ, подпись, `built`, причина, дайджест, размер, ресурсы, состав из манифеста) и шаблоны. Его читают консоль и блок промпта.
- Шаблоны живут в каталоге сервера, а не в коде консоли. Оператор контура убирает «Веб», если выход в интернет запрещён.
- «Песочница по умолчанию» и другие старые окружения имеют `config.image = null` и остаются на `legacy` до EX4 (1.3).

### 1.6 Ключ и дайджест образа

Ключ каталога выбирает образ, дайджест задаёт его содержимое.

- `build.sh` пишет дайджест манифеста OCI из `index.json` в `<каталог>.manifest.json` полем `image_digest`.
- `build.sh` не перезаписывает существующий каталог версии. Новая сборка получает новую версию и новую запись каталога.
- Сервер при загрузке каталога сверяет дайджест из `index.json` с записанным. Расхождение даёт `built: false` с причиной «каталог образа изменён после сборки».
- Образ из реестра указывается только ссылкой с `@sha256:`. Ссылку с одним тегом сервер не принимает.
- При создании VM runner кладёт в снимок VM (4.5) ключ, дайджест и хеш манифеста. Адаптер перед созданием VM ещё раз сверяет дайджест на диске со снимком. При расхождении VM не создаётся, ход получает ошибку `image_changed_on_disk`.
- Отпечаток VM и блок промпта берут дайджест и манифест из снимка, а не из текущего каталога. Смена `default_image` или записи каталога не меняет живую VM и её промпт, новые VM получают новый образ.

### 1.7 Правки адаптера и скрипта установки (после коммитов W4 и TS4)

- `exec` идёт через `bash -c`, если манифест образа говорит, что bash есть. На образе без манифеста адаптер проверяет `/bin/bash` один раз в `initializeBox`, на голом образе остаётся `sh -c`. Скрипты установки остаются POSIX.
- VM создаётся из образа снимка: `rootfsPath` каталога OCI или ссылка с дайджестом, диск, память и CPU из каталога.
- Пакеты окружения ставятся из слоя без сети (3.4). Старый скрипт `buildEnvironmentSetupScript` остаётся только для запуска без каталога и для других адаптеров. В нём pip ставит в Python, который первым стоит в PATH (`uv pip install --python "$(command -v python3)"`, иначе `python3 -m pip`), а apt пропускает `apt-get update`, если `dpkg -s` показывает все пакеты установленными.
- В сети «Ограниченный» адаптер не открывает vault-прокси и не ставит в VM `HTTP_PROXY`, `HTTPS_PROXY` и их пару в нижнем регистре (3.6). Сейчас прокси попадает в `allowNet` (`litebox.ts:789-801`), а клиент с `HTTPS_PROXY` проходит через него на любой хост (`litebox.ts:822-856`).
- Хосты реестров адаптер открывает только для менеджеров, которые есть в манифесте образа. Для `workplace` это PyPI, Debian и npm. Хосты Ubuntu, Alpine, crates, rubygems и Go из `PACKAGE_MANAGER_HOSTS` (`environment-setup.ts:39-52`) для образов каталога не открываются.
- Секреты по префиксу команды (`litebox.ts:631-637`) получает только строка из одной команды `git` без `;`, `&&`, `||`, `|`, перевода строки, `$(` и обратных кавычек. Сейчас строка `git status; pip install x` отдаёт токен git и коду pip.
- Счётчик одновременных VM и памяти из 1.3 общий для процесса.
- Сборочная VM (3.3) создаётся тем же адаптером в отдельном режиме.
- Если оператор задал зеркала, адаптер ставит в рабочей VM `PIP_INDEX_URL`, `UV_INDEX_URL` и `npm_config_registry`, пишет `/etc/apt/sources.list.d/oma-mirror.list` и выключает публичные источники apt. Только адреса, без учётных данных (3.7). Тогда агент ставит через зеркало и на образе, собранном без аргументов зеркал.
- После установки слоя адаптер снимает стартовый состав пакетов (5.2) и пишет в лог `box ready in <мс>`.
- Каждый скрипт установки ещё раз проверяет имена функцией из 3.2 и бросает ошибку на плохом имени. Экранирование `shellQuote` (`environment-setup.ts:131`) остаётся независимо от проверки.

## 3. Установка пакетов и доверие

### 3.1 Кому и чему доверяем

- Граница это VM BoxLite: микро-VM libkrun через `/dev/kvm` (`docs/runbook-local.md:12`). Выход из VM на хост план не проверяет и не обещает. Root внутри VM сам по себе такого выхода не даёт, но и доказательства обратного в плане нет.
- Код в рабочей VM: команды агента, пакеты, которые поставил агент, пакеты окружения. Всё это платформа считает кодом агента с правами root в VM. Такой код может подменить инструменты VM и прочитать всё, что VM видит. Поэтому платформа не верит ответам из VM (5.2), ограничивает содержимое VM (3.8) и её сеть (3.6).
- Источники пакетов задаёт оператор: публичные реестры или зеркала из `SANDBOX_PACKAGE_MIRRORS`. Других источников платформа не использует.
- Список пакетов окружения утверждает человек с правом правки окружения. Навык пакеты только объявляет (раздел 6). Оператор может сузить выбор файлом `SANDBOX_PACKAGE_POLICY`: запрещённые имена и белый список по менеджерам. Без файла проходит любое имя правильного формата.
- Версии и хеши закрепляет подготовка слоя (3.3). Сессии окружения получают одни и те же файлы, пока пользователь не изменит список или не нажмёт «Обновить пакеты».
- Пакет из доверенного источника всё равно может оказаться вредным. Отдельная сборочная VM защищает от кода установки, но код самого пакета выполнится, когда агент им воспользуется. От этого защищают только выбор пакетов человеком и сеть VM.

### 3.2 Проверка имён пакетов

Белый список формата. Строка проходит, только если целиком совпала с шаблоном своего менеджера. Всё остальное отклоняется.

| Менеджер | Формат | Проходят |
|---|---|---|
| pip | имя PEP 508 из `[A-Za-z0-9]`, `.`, `_`, `-` (начало и конец буква или цифра); необязательные extras `[a,b]` с такими же именами; необязательный список ограничений через запятую: оператор `==`, `!=`, `>=`, `<=`, `>`, `<`, `~=` и версия из чисел через точку с необязательной меткой `a`, `b`, `rc`, `.post`, `.dev`; у `==` и `!=` можно `.*` в конце | `numpy`, `numpy==2.0.2`, `pandas[excel]>=2.2,<3`, `python-pptx>=1.0` |
| npm | необязательный scope `@x/` и имя из `[a-z0-9]`, `.`, `_`, `-`; необязательно `@` и точная версия semver `1.2.3` или `1.2.3-beta.1` | `cowsay`, `@scope/pkg@1.2.3` |
| apt | имя Debian из `[a-z0-9]`, `+`, `.`, `-`, не короче двух знаков, без версии и архитектуры | `python3-bs4`, `libreoffice-impress-nogui` |
| cargo, go, gem | при включённом каталоге не принимаются: в образах каталога этих инструментов нет. Без каталога прежнее поведение | |

Общие правила: только ASCII, длина от 1 до 214 знаков, без пробелов. Отклоняются, в том числе:

- опции: `-e .`, `--index-url=https://x`, `-r req.txt`, любое начало с `-`;
- адреса и прямые ссылки: `https://x/p.whl`, `file:///x`, `name @ https://x`, `git+https://x`, `github:user/repo`;
- пути: `./x`, `/x`, `../x`, `~/x`, `x/../y`;
- маркеры окружения после `;`, кавычки, `$()`, обратные кавычки, `\`, перевод строки, табуляция;
- похожие буквы другой азбуки, например `раndas` с кириллической «р»;
- теги npm (`pkg@latest`, `pkg@next`) и диапазоны npm (`^1.2`);
- для apt версия и архитектура: `pkg=1.0`, `pkg:amd64`;
- для pip `===1.0` и локальные версии `1.0+local`.

Проверка одна, `P/sandbox/src/environment/package-names.ts` (EX2). Её зовут все входы: API окружения через порт политики (ES1), загрузка навыка (ES4), закрепление и разбор установленного (ES4), подготовка слоя (ES7), скрипты установки (ES2). Отрицательные случаи из списка выше проходят тест на каждом входе.

### 3.3 Подготовка слоя окружения

Пакеты окружения платформа готовит один раз на набор и кладёт в каталог слоя на хосте.

- Ключ слоя: sha256 от версии формата, дайджеста образа, нормализованного списка пакетов окружения, адресов источников и хеша `SANDBOX_PACKAGE_POLICY`. Порядок пакетов в списке на ключ не влияет.
- Каталог: `SANDBOX_LAYER_DIR/<ключ>` (по умолчанию `./data/sandbox-layers`, на машине разработчика `~/.cache/ai-backoffice-v3/environments/layers`).
- Если каталога нет, runner перед созданием рабочей VM зовёт подготовку и ждёт её. В трейсе это фаза `prepare_layer` в том же колбэке фаз, что вводит TS4 плана agent-trace.
- Сборочная VM: тот же дайджест образа, что у рабочей; сеть только к источникам пакетов (3.6); один том, каталог `<ключ>.tmp` в `/out`; в окружении процесса только адреса зеркал. Файлов сессии, хранилищ памяти, переменных хранилищ секретов, токенов git и шлюза модели в ней нет.
- pip. `uv pip compile` разрешает список с ограничениями из `pip freeze` образа и пишет `pip.lock` с хешами. Пакеты, которые уже есть в образе той же версии, в слой не идут. Остальное скачивает `pip download --require-hashes`. sdist собирает в wheel `pip wheel --no-deps` прямо в сборочной VM, хеши собранных wheel идут в `pip.wheels.sha256`.
- apt. `apt-get update` и `apt-get install --download-only --no-install-recommends`. apt сверяет подписи архива Debian. Файлы `.deb` и их sha256 идут в `/out/apt`.
- npm. `npm install -g --prefix /out/npm`. Скрипты пакетов выполняются здесь, в сборочной VM. Версии и integrity из `npm ls -g --json` идут в `npm.lock`.
- Пакет, который при сборке качает файлы с хоста вне источников (релизы GitHub, CDN), падает. Хвост лога с именем хоста видит пользователь. Это намеренно, такой пакет нужно положить в зеркало.
- После успеха `<ключ>.tmp` переименовывается в `<ключ>`, лог остаётся в `prepare.log`. lock копируется в KV сервера по окружению. Если каталог слоя удалён, а lock есть, подготовка повторяется по lock с `--require-hashes` и даёт те же файлы.
- «Обновить пакеты» сбрасывает lock окружения, следующая сессия разрешает версии заново.
- Слои, которые 14 дней не использовал ни один снимок VM, сервер удаляет при старте.

### 3.4 Установка слоя в рабочую VM

- Каталог слоя монтируется в рабочую VM только на чтение в `/opt/oma/layer`.
- pip: `uv pip install --offline --no-index --find-links /opt/oma/layer/pip --require-hashes -r /opt/oma/layer/pip.install.lock --python /opt/venv/bin/python`. Из wheel код при установке не выполняется.
- apt: сверка sha256 по списку, затем `dpkg -i` всех файлов слоя. Скрипты пакетов Debian выполняются в рабочей VM от root. Это единственный чужой код установки в рабочей VM, его источник подписан архивом Debian.
- npm: симлинки `bin/*` из `/opt/oma/layer/npm` в `/usr/local/bin`. Скрипты npm в рабочей VM не выполняются.
- Установка идёт с пустым окружением процесса и без сети. Таймаут 120 с.
- На образе `legacy` нет venv и uv. Окружение `legacy` с pip-пакетами получает ошибку подготовки «образ не умеет pip, выберите workplace», а не код 127 посреди старта.

### 3.5 Установка по требованию: агент ставит сам

- Это обычная команда агента в рабочей VM. У неё те же права, что у любой команды агента: root в VM, файлы сессии и секреты своего harness из 3.8. Отдельно платформа её не разрешает и не запрещает, решает сеть окружения.
- «Без ограничений»: агент ставит из публичных реестров.
- «Ограниченный» с менеджерами пакетов: агент ставит из источников 3.6, остальные хосты закрыты.
- «Ограниченный» без менеджеров пакетов: реестры закрыты, блок говорит агенту не пробовать. Пакеты из списка окружения в VM уже есть.
- Поставленное агентом живёт до остановки VM. В окружение оно попадает только кнопкой пользователя (раздел 5) и дальше идёт путём платформы через слой.

### 3.6 Сеть «Ограниченный» и источники пакетов

| Куда | Сборочная VM | Рабочая VM, «Без ограничений» | Рабочая VM, «Ограниченный» с менеджерами | Рабочая VM, «Ограниченный» без менеджеров |
|---|---|---|---|---|
| источники пакетов: зеркала из `SANDBOX_PACKAGE_MIRRORS`, без них PyPI (`pypi.org`, `files.pythonhosted.org`), Debian (`deb.debian.org`, `security.debian.org`), npm (`registry.npmjs.org`) | да, только менеджеры образа | да | да, только менеджеры образа | нет |
| `allowed_hosts` окружения | нет | да | да | да |
| vault-прокси (`OMA_VAULT_PROXY_URL`) | нет | да | нет | нет |
| остальные хосты | нет | да | нет | нет |

- Зеркало задаётся по менеджеру. Для менеджера с зеркалом публичный реестр в сборочной VM и в «Ограниченном» не открывается.
- Сборочная и рабочая VM берут адреса зеркал из переменных процесса (`PIP_INDEX_URL`, `UV_INDEX_URL`, `npm_config_registry`) и файла источников apt, которые ставит адаптер (1.7), а не из образа. Поэтому один образ подходит и для публичных реестров, и для контура. Аргументы сборки из 1.2 нужны, только если образ для контура собирают заранее.
- `allowed_hosts` не становятся источниками для платформы. Пользователь может разрешить хост своего зеркала, и агент поставит с него сам, например `pip install --index-url https://<хост>/simple <имя>`. Подготовка слоя берёт пакеты только из источников оператора.
- Флажок менеджеров пакетов управляет только самостоятельной установкой агента. Список окружения ставится из слоя при любой сети. Поэтому пакет, добавленный в окружение, работает и при закрытых реестрах, а явно разрешённый хост зеркала в `allowed_hosts` для этого не нужен. Ход останавливается с `skill_dependency_unmet`, только если требования навыка не выполнены и агенту некуда ставить (6.3). Ошибка сразу предлагает добавить пакеты в окружение.
- vault-прокси в «Ограниченном» закрыт, потому что клиент с `HTTPS_PROXY` проходит через него на любой хост (`litebox.ts:822-856`). Подстановка секретов хранилищ через oma-vault в «Ограниченном» поэтому недоступна. На Node oma-vault всё равно нет (`docs/runbook-local.md:192-194`). Открыть прокси можно, когда он сам будет проверять политику сессии. Это отдельная задача, её проверки те же, что у `net.vault_proxy_closed`: `CONNECT` и перенаправление на запрещённый хост.
- Шлюз модели для Claude Code (`ANTHROPIC_BASE_URL` на main-node) открывает план моделей. Его токен песочницы открывает только маршрут прокси своей сессии (S2 в [models-harness-analytics.md](models-harness-analytics.md)).
- Перенаправления. BoxLite фильтрует каждое соединение по SNI и Host на портах 80 и 443 (`litebox.ts:582`). Перенаправление на другой хост открывает новое соединение и проходит ту же проверку. Это подтверждает `net.redirect_closed`. web_fetch на стороне main-node проверяет каждый переход сам (`A/harness/web-fetch-http.ts:1-3`).
- Реестры с учётными записями. Через `registry.npmjs.org` можно опубликовать пакет чужим токеном, через `pypi.org` менять данные чужой учётной записи. Код в VM с открытыми реестрами может так вывести данные. Это цена флажка менеджеров пакетов, консоль пишет о ней под флажком (2.2). Зеркала контура должны быть только на чтение (вопрос в разделе 10).

### 3.7 Учётные данные зеркал

- `SANDBOX_PACKAGE_MIRRORS` содержит только адреса. Сервер не стартует, если в адресе есть логин или пароль (`user:pass@`), строка запроса или фрагмент. Ошибка называет переменную, но не печатает значение.
- `build.sh` проверяет аргументы сборки так же. Значения ARG видны в `docker history`, поэтому секреты через аргументы не передаются никогда.
- Зеркала с авторизацией в этой версии не поддерживаются. Оператор открывает чтение без логина из сети песочниц или ставит перед зеркалом свой прокси с авторизацией. Оба варианта это вопрос к банку (раздел 10).
- Проверка: `scan-secrets.sh` ищет `://…@`, `token=`, `password=` и `_authToken` в `/etc/pip.conf`, `/etc/uv/uv.toml`, `/etc/apt/sources.list.d/*`, `/etc/npmrc`, манифесте, слоях образа и `docker history --no-trunc`. Тест ES3 подаёт адрес с логином и ждёт ошибку старта. `pkg.layer_isolation` в EV1 идёт через зеркало и проверяет `prepare.log`.

### 3.8 Что видит код в рабочей VM

| Что | Встроенный цикл (Pi) | Claude Code в VM (`acp-sandbox`) | Сборочная VM |
|---|---|---|---|
| файлы `/workspace`, `/mnt/session/outputs`, хранилища памяти `/mnt/memory` | да | да | нет |
| переменные хранилищ секретов | нет, только для `acp-sandbox` (`N/lib/node-managed-vault-env.ts:47`) | да, открытым текстом | нет |
| токен шлюза модели | нет, модель зовёт хост | да, токен песочницы из S2: только маршрут прокси своей сессии | нет |
| токен git ресурса-репозитория | только строка из одной команды `git` (1.7). Сейчас любая строка, которая начинается с `git` (`node-managed-session-inputs.ts:308`, `litebox.ts:634`) | так же | нет |
| сеть | политика окружения (3.6) | политика окружения и шлюз модели | только источники пакетов |

## 4. Блок «Окружение» в системном промпте

### 4.1 Зачем

`platformGuidance` говорит про авторизацию, три сбоя и `/mnt/session/outputs/` (`A/harness/platform-guidance.ts:7-26`). Про ОС, root, сеть и установку пакетов там нет ни слова. Описание bash тоже молчит (`A/harness/tools.ts:447-454`). Шаблон «Глубокий исследователь» песочницу не упоминает (`C/data/templates.ts:92-106`).

### 4.2 Из чего собирается

- Чистая функция `buildEnvironmentPrompt({executor, snapshot, manifest, webSearch, acpClient})` в новом `A/harness/environment-prompt.ts` возвращает текст блока.
- `executor` говорит, где на деле выполняются команды агента:
  - `vm`: VM BoxLite из каталога;
  - `host`: LocalSubprocess на хосте сервера, пакеты и сеть окружения там не применяются;
  - `remote`: `acp-proxy`, процесс на чужой машине в каталоге репозитория (`A/harness/acp-proxy-delivery.ts:31`);
  - `unknown`: E2B, Daytona, BoxRun и другие адаптеры без манифеста.
- main-node выбирает исполнителя по адаптеру песочницы и harness агента.
- Для `vm` факты берутся из снимка VM (4.5) и манифеста его дайджеста: ОС, архитектура, пользователь, оболочка, venv, предустановленное, сеть в том виде, в каком её применил адаптер, пакеты слоя с версиями, требования навыков закреплённых версий, поиск.
- Для `host`, `remote` и `unknown` блок не называет ОС, пользователя, пути, оболочку и способ установки. Он говорит только то, что платформа знает точно.
- Для ACP-клиентов в VM (Claude Code, Codex и другие) строка про установку начинается с «If your tool permissions allow shell commands». У клиента свои разрешения инструментов, блок их не отменяет и не расширяет.
- main-node кладёт блок первой записью `platformReminders` с `source: "environment"` в `buildHarnessContext` (`N/modules/node-managed.ts:634-649`). `composeSystemPrompt` дописывает его к промпту (`platform-guidance.ts:47-58`). Разбор навыков пропускает записи без префикса `skill:` (`A/harness/assembly/skills/resolve-context.ts:17`).
- Блок не меняется, пока живёт VM: он зависит только от снимка, а снимок меняется только с новой VM. Кэш промпта поэтому не страдает. Размер 900-1500 знаков, около 300 токенов.
- Блок на английском, как остальной `platformGuidance`. Списки библиотек обрезаются до 20 имён.

### 4.5 Снимок VM и отложенные изменения

- Снимок VM: поколение VM, ключ, дайджест и хеш манифеста образа; сеть в том виде, в каком адаптер её применит (`allowNet`); ключ слоя и его lock; закреплённые версии навыков с их требованиями; исполнитель; время создания. Чистые функции снимка и отпечатка лежат в `P/sandbox/src/environment/sandbox-snapshot.ts` (EX3).
- Перед ходом runner строит желаемый снимок из текущей конфигурации. Если VM нет, он закрепляет этот снимок за новой VM, адаптер применяет ровно его. После старта адаптер добавляет `ready_ms` и стартовый состав пакетов (5.2).
- Если VM жива, `decideSandboxReuse(live, desired)` решает так:
  - сеть изменилась: VM пересоздаётся перед ходом, потому что политика сети должна действовать сразу;
  - изменились образ, пакеты или версии навыков: VM остаётся, разница становится отложенным изменением;
  - снимки равны: VM остаётся.
- Блок промпта строится из снимка живой VM. После добавления пакета в окружение промпт текущей VM пакета не обещает. После удаления пакета из окружения сессия показывает, что пакет в её VM ещё есть.
- `GET /v1/oma/sessions/:id/sandbox` отдаёт снимок живой VM и список отложенных изменений. `POST /v1/oma/sessions/:id/sandbox/recreate` работает только в `idle`: останавливает VM, следующий ход создаёт новую по текущей конфигурации.
- Консоль показывает над полем ввода: «Окружение изменилось: новые пакеты, другой образ. Изменения применятся после пересоздания песочницы. Файлы вне /mnt/session/outputs пропадут», кнопка «Пересоздать песочницу» (EK2).
- Сейчас отпечаток VM включает весь `environment.config` (`N/lib/node-managed-session-runner.ts:232-236`), и любое закрепление пересоздало бы VM и стёрло `/workspace`. Новый отпечаток берёт определяющие поля снимка. Правка в раннере это замена этих строк вызовом `decideSandboxReuse`.
- VM живут в процессе сервера. После рестарта VM нет, снимки в KV помечаются завершёнными.

## 5. Закрепление пакета в окружении

### 5.1 Что видит пользователь

- После хода, в котором агент что-то поставил, страница сессии показывает над полем ввода строку: «Агент поставил в этой сессии: pip beautifulsoup4==4.12.3, apt python3-bs4. Они пропадут вместе с песочницей». Рядом кнопка «Добавить в окружение» и пометка «Сведения из песочницы сессии. Агент мог их изменить, проверьте список».
- Обновлённый пакет образа показан отдельно: «обновлён numpy 1.26.4 → 2.0.2».
- Окно «Добавить пакеты в окружение «Песочница по умолчанию»». Флажок на каждый пакет, все включены, рядом точная строка, которая уйдёт в окружение. Предупреждение: «Платформа подготовит пакеты для новых сессий этого окружения. Текущая сессия не перезапускается». Кнопки «Отмена» и «Добавить».
- На карточке окружения блок «Предложено из сессий»: пакеты, которые агенты ставили в сессиях этого окружения за 30 дней, с числом сессий и кнопкой «Добавить».
- Локальные npm-пакеты проекта из `/workspace/package.json` видны в строке с пометкой «локальные», в окружение они не предлагаются: это зависимости проекта, а не инструменты.
- Без кнопки пользователя окружение не меняется. Агент сам окружение не правит.

### 5.2 Как сервер узнаёт

- Стартовый состав. Сразу после установки слоя адаптер выполняет в VM скрипт состава и кладёт ответ в снимок. В состав входят полный список pip из venv с версиями (`/opt/venv/bin/python -m pip list --format=json`), все пакеты dpkg с версиями (`dpkg-query -W -f '${Package}\t${Version}\n'`), глобальные npm с версиями (`npm ls -g --depth=0 --json`) и верхний уровень `/workspace/package.json`, если он есть.
- Новый `GET /v1/oma/sessions/:id/installed-packages`. Если VM сессии жива (`connectedSandbox`, `N/lib/node-managed-session-runner.ts:220-222`), сервер одним вызовом выполняет тот же скрипт и сравнивает ответ со стартовым составом: новые, обновлённые и удалённые пакеты с версиями.
- Пределы. Таймаут вызова 10 с, ответ не больше 256 КБ. Сверх предела ответ помечается `truncated` и в разницу не идёт.
- Каждое имя из ответа VM сервер ещё раз проверяет функцией из 3.2. Плохие имена отбрасываются, их число приходит в поле `rejected`. Весь ответ помечен `source: "sandbox"`, консоль показывает пометку из 5.1.
- Ответ сохраняется в KV по сессии, поэтому он доступен и после остановки VM. Без живой VM маршрут отдаёт последний сохранённый.
- Консоль зовёт маршрут, когда сессия встала в `idle` после хода с вызовом bash. Вызов идёт только по запросу, оценка 0,3-1 с.
- pip и npm идут с версией (`beautifulsoup4==4.12.3`, `pkg@1.2.3`), apt без версии, потому что в Debian она меняется с обновлениями безопасности.
- `GET /v1/oma/environments/:id/package-suggestions` собирает сохранённые ответы сессий окружения для блока «Предложено из сессий». Старый роутер `/v1/oma/environments` сняла очистка 2026-10-19 ([cleanup.md](cleanup.md), 4.6), поэтому новый маршрут подключается в `N/modules/node-http.ts` отдельно.

### 5.3 Запись и VM текущей сессии

- «Добавить» делает `POST /v1/environments/:id` с объединённым списком. Права те же, что у правки окружения, порт политики проверяет имена ещё раз. Если builder BP1 уже добавил `If-Match`, консоль передаёт ревизию.
- Новые пакеты меняют ключ слоя. Первая следующая сессия ждёт подготовки (3.3).
- Текущая VM не пересоздаётся, её снимок не меняется. Сессия видит отложенное изменение (4.5).

### 5.4 Позже: агент-помощник

В плане builder-agent у ассистента есть `update_environment` с карточкой разницы (`builder-agent.md:182`, раздел 2.5). Добавить инструмент класса «чтение» `session_installed_packages(session_id)` поверх маршрута 5.2. Тогда ассистент сам предлагает: «Агенты трёх сессий ставили beautifulsoup4, добавить в окружение?», а пользователь подтверждает карточкой. Это строка для BS1 и BC1 после обеих волн 2, в единицы этого плана не входит.

## 6. Зависимости навыков

### 6.1 Формат

Спецификация agentskills.io знает поля `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`. Поля зависимостей в ней нет, референсный валидатор отклоняет любое другое поле верхнего уровня. Поэтому зависимости лежат в `metadata` с префиксом `oma.requires.`:

```yaml
---
name: office-pptx
description: Создаёт и правит презентации .pptx на python-pptx и проверяет их рендером в PNG. Брать, когда нужен файл PowerPoint.
compatibility: Нужны python-pptx и LibreOffice (soffice). Без LibreOffice навык не проверит рендер.
metadata:
  oma.requires.pip: "python-pptx>=1.0"
  oma.requires.apt: "libreoffice-impress-nogui"
---
```

Значения это строки формата 3.2 через пробел: для pip имя с ограничениями версии, для npm имя или имя с точной версией, для apt имя. Claude Code и Codex такие ключи пропускают, навык остаётся переносимым. `compatibility` пишется для людей и других клиентов.

### 6.2 Загрузка

- Сейчас frontmatter читается построчно регулярным выражением (`N/lib/node-skills-routes.ts:63-74`, `N/lib/skill-sources.ts:353-362`), вложенный `metadata` и ключи с точкой оно не разбирает.
- Загрузка zip и установка по адресу разбирают frontmatter через js-yaml (новый `N/lib/skill-requirements.ts`), проверяют строки по 3.2 и пишут `requirements: {apt, pip, npm}` в запись версии рядом с `files` (`node-skills-routes.ts:291, 377`). Плохая строка или неподдерживаемое ограничение версии даёт 400 с названием ключа.
- API навыка и версии отдаёт `requirements`. Консоль показывает чипы «pip python-pptx>=1.0» в строке навыка на странице «Навыки».
- Версии, загруженные до правки, сервер разбирает при первом чтении и дописывает.

### 6.3 Решение и проверка при старте VM

Навык только объявляет. Ставит пакеты окружение, решает человек с правом правки окружения.

- При построении желаемого снимка (4.5) runner закрепляет версии навыков агента, своих и встроенных: `latest` превращается в конкретную версию так же, как в `resolveNodeManagedSkillMounts` (`N/lib/node-managed-session-inputs.ts:116-158`). Монтирование и требования берутся из этих версий, пока живёт VM. Новая версия навыка, загруженная во время сессии, становится отложенным изменением.
- Требование выполнено, если пакет есть в полном составе образа или в lock слоя окружения и его версия подходит под все ограничения. Сравнение версий pip идёт по подмножеству PEP 440 из 3.2, npm по точной версии, apt только по имени.
- Если два навыка требуют одно имя, проверка берёт версию из образа или lock и сверяет её с ограничениями обоих. Если версия не подходит хотя бы одному, это конфликт, и ошибка называет оба навыка.
- Если требование не выполнено, а агент может ставить сам («Без ограничений» или «Ограниченный» с менеджерами пакетов), ход идёт. Блок «Окружение» пишет строку `Skill requirements not installed`, консоль показывает над полем ввода: «Навык office-pptx требует pip python-pptx>=1.0, в окружении его нет. Агент поставит его сам в этой сессии». Рядом кнопка «Добавить в окружение». Платформа сама при этом ничего не ставит, ставит агент своей командой (3.5).
- Если требование не выполнено, а реестры закрыты («Ограниченный» без менеджеров пакетов), ход останавливается до создания VM с ошибкой `skill_dependency_unmet`: «Навык office-pptx требует pip python-pptx>=1.0. В образе python-pptx 0.6.23, в пакетах окружения его нет, а сеть окружения закрыта для реестров». Хвоста вывода apt пользователь не видит.
- Консоль показывает эту ошибку над полем ввода с кнопкой «Добавить в окружение». Кнопка открывает окно из 5.1 со строками требований. После добавления следующий ход готовит слой и стартует при любой сети.
- Выполненные требования попадают в блок «Окружение» строкой `Skill requirements met`.
- Встроенные навыки платформы (тип `anthropic`, папка `platform/skills/builtin`, план [document-skills.md](document-skills.md)) идут тем же путём. Их версия это хеш файлов, старая версия после правки файлов пропадает. Закрепление живёт, пока живёт VM, а VM не переживает рестарт сервера, поэтому пропавшая версия ему не мешает.

### 6.4 Навыки для документов

План [document-skills.md](document-skills.md) пишется параллельно. Он берёт четыре навыка NousResearch/hermes-agent под MIT, кладёт их в `platform/skills/builtin` и подключает типом `anthropic`. Пакеты для них сейчас ставит шаблон «Документы» в коде консоли (`C/lib/environment-templates.ts`): apt `python3-pip fonts-dejavu-core` и шесть pip-пакетов. Если пакетов нет, SKILL.md велит агенту поставить их самому. Этот проект согласуется с ним так:

- навыки docx, pdf, pptx и xlsx из anthropics/skills не копируем. Они source-available, а лицензия запрещает хранить копии вне сервисов Anthropic (`builder-agent.md:422`). План document-skills это соблюдает;
- каждый встроенный навык документов получает в frontmatter `metadata` с `oma.requires.*`. Компилятор навыков вложенные строки пропускает (`P/managed-agents-adapters-runtime/src/skill-package-compiler.ts:54-66`), требования разбирает `skill-requirements.ts`. Правку SKILL.md делает ES4 после коммита потока document-skills (9.4);
- в `workplace-office` все требования выполнены без установки. На `legacy` и `workplace` агент ставит недостающее сам по 6.3, при закрытых реестрах ход останавливается с `skill_dependency_unmet` и кнопкой «Добавить в окружение»;
- при включённом каталоге шаблоны «Нового окружения» приходят с сервера (1.5), и «Документы и офис» с `workplace-office` заменяет кодовый шаблон «Документы». Метка `metadata.oma_template = "documents"` у них общая. Без каталога консоль показывает кодовые шаблоны как сейчас (EK1);
- навык проверяет результат рендером: `soffice --headless --convert-to pdf`, затем `pdftoppm -png`, и смотрит картинки. Для этого нужен `workplace-office`;
- reportlab рисует кириллицу только со шрифтом TTF. Навык регистрирует `DejaVuSans` из `/usr/share/fonts/truetype/dejavu/`. Образ проверяет это `render-ru.py` (1.4).

## 7. Веб-поиск

### 7.1 Сейчас

- web_search скрейпит DuckDuckGo через неофициальный интерфейс (`A/harness/tools.ts:990-1052`). При блокировке агент получает «DuckDuckGo rate limited».
- Запрос идёт из процесса main-node обычным fetch (`A/harness/tool-http-fetch.ts:31-41`), а не из VM. Сеть окружения поиск не ограничивает.
- Tavily в коде есть (`tools.ts:1055-1090`), но на Node тип `web_search_tavily` недоступен, ключ не передаётся (`N/modules/node-managed.ts:571-583`). Ключ уходит в теле запроса (`tools.ts:1071`), а документация Tavily описывает заголовок `Authorization: Bearer`.
- web_fetch шлёт User-Agent `OMA-Agent/1.0 (+web_fetch)` (`tools.ts:770`), и защита Cloudflare отдаёт на него страницу проверки. Текст «fetch failed» без причины, потому что `httpFetchErrorMessage` берёт только `err.message` (`tool-http-fetch.ts:43-51`).

### 7.2 Провайдер по настройке

- Настройка `WEB_SEARCH_PROVIDER` принимает `searxng`, `brave`, `tavily`, `duckduckgo` или `off`. Без настройки остаётся `duckduckgo`, только для разработки.
- Ключи и адреса: `SEARXNG_URL`, `BRAVE_SEARCH_API_KEY`, `TAVILY_API_KEY`. Brave берёт ключ в заголовке `X-Subscription-Token`, Tavily в `Authorization: Bearer`.
- Провайдеры живут в новом `A/harness/web-search-providers.ts`, ответ каждого приводится к `{title, url, description}`. `tools.ts` выбирает провайдера по настройке, которую main-node передаёт в `buildTools`.
- `off` убирает инструмент, блок «Окружение» пишет `Web search: not available.`
- web_fetch шлёт User-Agent с контактом из настройки `WEB_FETCH_USER_AGENT` и пишет в текст ошибки код причины из `cause.code` (`ENOTFOUND`, `ECONNRESET`, ошибка сертификата). Защиту Cloudflare не обходим.
- В консоли подпись «Веб-поиск через DuckDuckGo» (`C/pages/agents/AgentFormDialog.tsx:73`) становится «Веб-поиск».

### 7.3 Политика окружения

Фильтр результатов не защищает сам запрос: текст запроса уходит провайдеру до фильтра. Поэтому поиск разрешает окружение, и проверка стоит до HTTP.

- Новое поле `networking.allow_web_search` у сети «Ограниченный». Это наше расширение API, как `config.image`. По умолчанию `false`, в том числе у всех существующих окружений с «Ограниченным». В «Без ограничений» поиск разрешён всегда.
- Чистая функция `webSearchPolicy(networking, provider)` в `A/harness/web-search-policy.ts` даёт `off`, `on` или `filtered` со списком хостов.
- `off`: `buildTools` не регистрирует web_search. Сам инструмент перед вызовом провайдера ещё раз сверяет политику и при `off` отвечает ошибкой без HTTP-запроса.
- `filtered`: запрос уходит, результаты фильтруются по `allowed_hosts` тем же сравнением, что у web_fetch (`A/harness/web-fetch-http.ts:28-34`). Сравнение учится понимать маску `*.example.com`, сейчас она не совпадает никогда.
- Блок «Окружение» пишет строку поиска из 4.3.
- Проверка `net.search_policy` считает запросы к фейковому SearXNG. Запрещённый поиск не даёт ни одного.

### 7.4 Закрытый контур

- Свой SearXNG единственная точка поиска, платформа ходит только в него.
- Без интернета SearXNG работает на офлайн-движках по внутренним базам: Elasticsearch, Meilisearch, Solr, SQL. Публичного веба в этом режиме нет.
- С выходом через DMZ SearXNG ходит наружу через `outgoing.proxies` на корпоративный прокси, набор движков ограничен.
- Если main-node ходит наружу через прокси, ему нужны `NODE_USE_ENV_PROXY=1`, `HTTPS_PROXY` и `NO_PROXY`. Без них fetch Node прокси не видит, и web_search с web_fetch падают.
- Brave и Tavily отправляют текст запроса за периметр. Нужны договор и разрешение юристов. SearXNG под AGPL-3.0 ставится отдельным сервисом без правок, вопрос к юристам тоже.

## 10. Решения, вопросы, что не входит

Решения:

1. Образ собираем сами `FROM node:22-bookworm`. `openma/sandbox-base` собран на `cloudflare/sandbox`, с BoxLite не проверен, и в нём всё равно нет bs4, python-pptx и LibreOffice.
2. Окружение выбирает образ ключом каталога в `config.image`. VM запоминает дайджест, отпечаток и промпт берут его из снимка. В контуре набор образов утверждает оператор.
3. LibreOffice живёт в варианте `workplace-office`, база без него легче на 300-400 МБ.
4. Python в venv `/opt/venv` с симлинками в `/usr/local/bin`. Системный pip с `--break-system-packages` не используем.
5. Граница доверия это VM. Код в VM считается кодом агента, платформа ограничивает содержимое VM и её сеть.
6. Пакеты окружения платформа готовит в сборочной VM без секретов и файлов сессии, с закреплёнными версиями и хешами. В рабочей VM слой ставится без сети, чужой код установки там выполняют только пакеты Debian.
7. Навык только объявляет зависимости в `metadata` с префиксом `oma.requires.`. Решает окружение, проверка идёт до VM.
8. В сети «Ограниченный» vault-прокси закрыт, поиск выключен без `allow_web_search`.
9. Блок «Окружение» строится по снимку VM и исполнителю, лежит в `platformReminders` с `source: "environment"`, написан на английском. В ACP-клиенты он идёт механизмом клиента в `run`.
10. Смена сети пересоздаёт VM на следующем ходе. Смена образа, пакетов и версий навыков ждёт кнопки «Пересоздать песочницу».
11. Пакет попадает в окружение только по кнопке пользователя.
12. Провайдер поиска задаёт настройка сервера. DuckDuckGo остаётся только для разработки, для контура SearXNG.
13. Старые окружения остаются на `legacy`, пока замеры не уложатся в пределы и владелец не согласится.
14. Playwright и Chromium в базу не входят.
15. Шаблоны живут в каталоге сервера.

Вопросы владельцу:

- Сеть пустого окружения. Сейчас окно создания шлёт `config` без `networking` (`C/pages/EnvironmentsList.tsx:83-87`), и сервер ставит «Без ограничений». У Claude форма стартует с «Ограниченного». Шаблоны ставят «Ограниченный» с реестрами. Пустое окружение оставить как есть?
- Что есть у банка: реестр образов (например Harbor), зеркала PyPI, apt и npm, доступны ли они из сети песочниц на чтение без учётных данных, выход через прокси.
- Разрешён ли поиск через SaaS (Brave, Tavily) или только SearXNG.
- Принимаем ли риск реестров с учётными записями при флажке менеджеров пакетов (3.6) или в «Ограниченном» оставляем агенту только Debian, а npm и PyPI ставим только через слой.
- Переход старых окружений на `workplace` после замеров (EX4).

Не входит:

- удаление лого OpenMA, отдельная задача;
- агент не от root. pip в venv root не нужен, apt нужен. Владелец томов `/workspace` и `/mnt` и работа Claude Code из W4 под другим пользователем не проверены. Отдельная задача после этого плана;
- vault-прокси с политикой сессии: oma-vault в репозитории нет;
- зеркала с авторизацией;
- клонирование VM. В BoxLite 0.9 есть `snapshot`, `cloneBox` и `export` (`native-contracts.d.ts:182-200`). Слой окружения уже убирает повтор установки, клон ускорил бы сам старт. Скорость и размер клона не проверены;
- cargo, go и gem в образах каталога;
- закрепление локальных npm-пакетов проекта;
- образ с Playwright и подключение `browser` на Node;
- путь Cloudflare. Его код очистка удалила 2026-10-19 ([cleanup.md](cleanup.md), 4.2).

Не проверено: отсутствие pip в `node:22-bookworm`, перенос ENV образа в exec BoxLite, запуск BoxLite из каталога buildx, работа `libreoffice-*-nogui` на docx и pptx, размеры образов и время старта VM из 2,2 ГБ, приём `_meta.systemPrompt` в `claude-agent-acp`, чтение `/root/.claude/CLAUDE.md` в Claude Code внутри VM, `dpkg -i` слоя без сети на чистой VM, доступ VM с узким `allowNet` к адресу хоста с нестандартным портом, приём ключа Tavily в теле запроса, причина «fetch failed» в пробной консоли, выход из VM на хост.
