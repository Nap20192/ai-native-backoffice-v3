# CMA: секреты и безопасность

Разбор четырёх страниц документации Claude Managed Agents и сверка с нашей копией Open Managed Agents в `platform/`. Дата сверки 17.10.2026. Код смотрели на ветке `feat/agent-console` с незакоммиченными правками. Области ACP, карточек харнесов и CLI-моста не смотрели, их сейчас удаляют.

## 1. Коротко

В CMA секреты лежат в хранилищах (vault). Хранилище принадлежит рабочему пространству и собирает учётные данные одного конечного пользователя. Сессия получает список `vault_ids` при создании. Токены MCP добавляет прокси Anthropic, в песочницу они не попадают. Секрет для CLI или SDK лежит в песочнице как заглушка, настоящее значение подставляется в исходящий запрос на выходе, только для разрешённых хостов.

Страницы о безопасности дают список настроек по важности. Сеть `limited` с коротким списком хостов. Секреты только в хранилищах. Списки доменов у веб-инструментов. Подтверждение рискованных вызовов. Минимум инструментов. Ненадёжный ввод отдельно от сильных инструментов. Бюджет и порядок остановки. Отдельно описаны вебхуки для наблюдения, офлайн-проверка расшифровок и сроки хранения данных.

У нас API хранилищ совпадает с CMA, секреты шифруются в базе, токены MCP подставляет прокси на хосте. Подстановки секретов на выходе нет: прокси `apps/oma-vault` в копию не попал. Архив не стирает секреты и не доходит до учёток. Инструменты MCP по умолчанию работают без подтверждения, а в CMA спрашивают. Списки доменов у `web_fetch` хранятся, но рантайм их не читает. Вебхуков, бюджета в рантайме и офлайн-проверки нет.

## 2. Что говорит документация

Все четыре страницы помечены как beta и требуют заголовок `anthropic-beta: managed-agents-2026-04-01`. SDK ставит его сам для `client.beta.vaults.*`. Лимиты запросов на организацию: создание 300 в минуту, остальные операции 600 в минуту.

### 2.1 Хранилища и учётные данные (vaults)

Страница объясняет, как один раз зарегистрировать секреты стороннего сервиса и ссылаться на них по id. Агент описывает продукт, сессия описывает пользователя. Поэтому хранилище передают в сессию, а не в агента.

Хранилище: `id` вида `vlt_...`, `type: "vault"`, `display_name`, `metadata` для связи со своими записями, `created_at`, `updated_at`, `archived_at`. Учётные данные: `id` вида `vcrd_...`, `display_name`, `auth`. Тип `auth` бывает трёх видов.

| Тип | Ключ | Поля |
|---|---|---|
| `mcp_oauth` | `mcp_server_url` | `access_token`, `expires_at`, блок `refresh` с `token_endpoint`, `client_id`, `scope`, `refresh_token`, `token_endpoint_auth` (`none`, `client_secret_basic`, `client_secret_post` с `client_secret`) |
| `static_bearer` | `mcp_server_url` | `token` |
| `environment_variable` | `secret_name` | `secret_value`, `networking` (`limited` с `allowed_hosts` или `unrestricted`), `injection_location` с `header` и `body` |

Поля `token`, `access_token`, `refresh_token`, `client_secret`, `secret_value` только на запись, API их не возвращает.

Как работает подстановка.

- MCP. Когда агент подключается к серверу по URL, прокси Anthropic берёт токен из хранилища. URL сравнивается после нормализации: регистр схемы и хоста, порт по умолчанию и слэш в конце не мешают. Другой путь или поддомен уже не совпадёт. Без совпадения подключение идёт без авторизации. С блоком `refresh` Anthropic сам обновляет токен.
- Переменная окружения. В песочнице лежит непрозрачная заглушка. Anthropic меняет её на секрет в исходящем HTTPS-запросе, если хост есть в `allowed_hosts` учётки. Хост должен быть открыт и в сети окружения, иначе запрос не уйдёт. Подстановка идёт только в заголовки и тело, путь URL не трогается. Клиент, который проверяет формат ключа или считает подпись (AWS SigV4), сломается. Ответ сервиса приходит без маскировки, поэтому обмен секрета на токен делают сами и кладут в хранилище готовый токен.
- `injection_location`. При создании без объекта включены оба места. Объект с одним полем выключает второе. При обновлении поля сливаются по одному. Оба `false` или явный `null` дают 400. Заглушка в выключенном месте уходит как есть. Claude Console создаёт учётку только с заголовком.

| Метод | Путь | Что делает |
|---|---|---|
| POST, GET | `/v1/vaults` | Создать, список (новые первыми, `include_archived`) |
| GET, POST, DELETE | `/v1/vaults/{vault_id}` | Прочитать, обновить, удалить навсегда |
| POST | `/v1/vaults/{vault_id}/archive` | Архив, каскадом на учётки |
| POST, GET | `/v1/vaults/{vault_id}/credentials` | Создать, список |
| GET, POST, DELETE | `/v1/vaults/{vault_id}/credentials/{credential_id}` | Прочитать, обновить (ротация), удалить |
| POST | `.../credentials/{credential_id}/archive` | Архив учётки |
| POST | `.../credentials/{credential_id}/mcp_oauth_validate` | Проверить OAuth-учётку |

Правила и ограничения.

- Ключ (`mcp_server_url` или `secret_name`) уникален среди активных учёток хранилища, дубль даёт 409.
- `mcp_server_url`, `secret_name`, `token_endpoint`, `client_id` менять нельзя. Для смены учётку архивируют и создают новую.
- В хранилище не больше 20 учёток.
- Секрет проверяется только во время сессии. Плохой токен даёт событие ошибки, сессия идёт дальше.
- `vault_ids` задаются при создании сессии. Обновление сессии их не меняет. При нескольких совпадениях берётся первое хранилище. В мультиагентной сессии учётки видят все потоки.
- `environment_variable` пока не работает с self-hosted песочницей. Документация советует свой прокси, который меняет заглушки на секреты.

Жизненный цикл. Сервер периодически перечитывает учётки, поэтому ротация, архив и удаление доходят до живых сессий без рестарта. Архив хранилища архивирует все учётки и стирает секреты, записи остаются для аудита. Новые сессии с таким хранилищем падают, живые продолжают. Архив учётки стирает секрет и освобождает ключ. Удаление стирает запись совсем. Архив окончательный, разархивации нет.

Вебхуки: `vault.archived`, `vault.deleted`, `vault_credential.archived`, `vault_credential.deleted`, `vault_credential.refresh_failed`. Проверка `mcp_oauth_validate` возвращает объект `vault_credential_validation` со `status`: `valid` (всё хорошо), `invalid` (просить пользователя войти заново), `unknown` (временная ошибка, повторить позже). В ответе ещё `has_refresh_token`, `mcp_probe` с шагом и HTTP-ответом и `refresh.status`.

### 2.2 Защита развёртывания (secure deployment)

Страница перечисляет настройки по убыванию важности. Пример везде один: агент поддержки читает тикет, ищет заказ через свой инструмент и пишет ответ.

| Настройка | Совет |
|---|---|
| Где работает агент | Облако, если инструменты не обязаны работать у вас. В self-hosted сеть и изоляцию держите сами, веб-инструменты ваш файрвол не ограничивает |
| `networking` окружения | `limited` и только нужные хосты. Без поля можно получить `unrestricted`. `allow_package_managers: false`, потому что он открывает весь github.com на запись. `allow_mcp_servers: false`, хосты MCP перечислить в `allowed_hosts`, тогда сессия с закрытым MCP-хостом не создастся |
| Учётки в хранилище | `injection_location` только заголовок, `networking` учётки `limited` с точными хостами, права ключа минимальные у выдавшего сервиса. Токен GitHub делать fine-grained |
| Ключ Claude API | Агенту не давать. Код в песочнице с таким ключом обходит все политики, бюджет и подтверждения |
| `allowed_domains` у `web_fetch` и `web_search` | Задать всегда. `blocked_domains` не защищает. Домен вне `allowed_hosts` даёт 400 при создании сессии |
| `permission_policy` | `read`, `glob`, `grep` разрешать. `bash`, `write`, `edit`, `web_fetch` на `auto`. `always_ask` для необратимых действий и для `bash`, если в агент идёт текст конечного пользователя. MCP на запись `always_ask`, это значение по умолчанию у MCP |
| Набор инструментов | `default_config.enabled: false`, включать только нужное. Обновление агента меняет весь `tools` и доходит только до новых сессий |
| Ненадёжный ввод | Агент, который читает тикеты, письма, страницы или результаты MCP, не держит на `always_allow` инструменты записи. Память подключать `read_only` |
| Лимиты и остановка | `budget` на сессию и деплоймент, `max_list_cost.amount` в центах строкой. Порядок: `user.interrupt`, пауза деплоймента, ротация ключа, ожидание `idle`, архив |

Совпадение хостов разное. В `allowed_hosts` запись `example.com` открывает только сам хост, `*.example.com` открывает поддомены без корня. В `allowed_domains` запись `example.com` открывает и поддомены.

`web_fetch` открывает только URL, которые уже были в сессии из сообщения пользователя, описания цели, результата поиска, текста скачанной страницы или результата своего инструмента. URL из системного промпта, вывода `bash`, результата MCP или файла он не откроет.

Политика `auto` значит, что сервер сам решает: выполнить, запретить или спросить. Это не проверка человеком. Приостановленная сессия ждёт бесконечно, поэтому нужен клиент, который отвечает на запросы. Клиент, который всё одобряет не глядя, равен `always_allow`.

При чтении `read` в облаке подгружаются `CLAUDE.md` и `AGENTS.md` из папок файла как инструкции, со ссылками `@` до пяти уровней. Выключить это нельзя, кроме отключения `read`.

Для агента, который и читает чужой ввод, и действует, страница даёт три схемы. Первая делит чтение и действие между агентами: ведущий, сборщик с веб-инструментами и исполнитель без них. Вторая даёт агенту один узкий свой инструмент, а ключ держит приложение. Третья ставит `always_ask` на сильный инструмент. Агенты одной сессии делят песочницу и учётки, поэтому для жёсткого разделения нужны две сессии с разными окружениями и хранилищами.

### 2.3 Риски и границы песочницы

Страница объясняет, зачем нужны настройки из 2.2. Скрытые инструкции в прочитанном тексте могут увести агента (prompt injection). Claude к этому устойчив, но поведение модели не мера защиты.

| Риск | Пример | Защита |
|---|---|---|
| Чужой ввод управляет агентом | Тикет велит отменить все заказы | Мало инструментов, ввод отдельно от сильных инструментов, подтверждения |
| Код в песочнице берёт учётку | Скрипт шлёт ключ на чужой хост | Секреты в хранилищах, сеть `limited`, подтверждения |
| Открытая сеть выпускает данные | `bash` отправляет файл наружу | Сеть `limited`, список доменов `web_fetch` |
| Агент делает неожиданный шаг | Берёт доступную учётку, чтобы обойти препятствие | Все настройки 2.2 и офлайн-проверка после |

Где что работает. Цикл агента, `web_search`, `web_fetch` и история сессии работают на серверах Anthropic. `bash` и файловые инструменты работают в песочнице, в облаке у каждой сессии свой контейнер. Секреты лежат вне песочницы. Свои инструменты работают в вашем приложении. Ограничения не заменяют друг друга: закрытая сеть не мешает агенту использовать учётку на открытом хосте. Настройки не защищают ваши инструменты, MCP-серверы и вашу инфраструктуру. Права ключа ограничивает только выдавший его сервис.

### 2.4 Проверка и наблюдение

Страница предлагает по желанию запускать офлайн-проверку. Это задача по расписанию, которая берёт события каждой сессии и отдаёт их Claude через Messages API. Сессии для проверки берут из вебхуков `session.status_idled` и `session.status_terminated` и из списка сессий, потому что доставка вебхука может потеряться. В мультиагентной сессии читают ещё события каждого потока.

Проверка ищет три вещи. Выход за выданное (чужая учётка, хосты, файлы, инструменты). Повторные попытки после отказа другим путём. Расхождение отчёта агента с событиями. Промпт велит считать весь текст расшифровки данными и отвечать JSON с полями `flag` и `evidence`. Список выданных инструментов, хостов и имён учёток кладут в `system`, не в сообщение. Ответ со `stop_reason: refusal` или не JSON значит, что сессию не проверили, и её смотрит человек. После флага сессию архивируют, ключи меняют, лишние права снимают.

| Что смотреть | Где |
|---|---|
| Сессия ждёт, например подтверждения | Вебхук `session.status_idled`, событие `session.status_idle` с `stop_reason.type: requires_action` и `event_ids` |
| Бюджет или завершение | `session.budget_reached`, `session.status_terminated` |
| Запуск по расписанию не стартовал | `deployment_run.failed`, `deployment.paused` |
| OAuth не обновился | `vault_credential.refresh_failed` |
| Вызовы, которые сервер запретил или остановил | `evaluated_permission` на `agent.tool_use` и `agent.mcp_tool_use` |

Подпись каждой доставки вебхука нужно проверять. Сроки хранения такие. История живёт до удаления сессии, архив её сохраняет, сессию в `running` удалить нельзя. Состояние песочницы живёт 30 дней. Файлы, созданные сессией, удаляются вместе с ней. Загруженные файлы, хранилища памяти и секретов удаляют отдельно. ZDR и HIPAA BAA для Managed Agents сейчас нет.

## 4. Что добавить

Сначала. Без этого секреты клиентов бэк-офиса защищены хуже, чем обещает API.

1. Поставить по умолчанию `always_ask` для MCP-инструментов. Бэк-офис подключает сервисы с деньгами и документами. Новый инструмент записи на сервере сейчас сразу работает без человека.
2. Архив учётки должен стирать секрет, архив хранилища должен архивировать учётки. Прокси MCP должен проверять архив хранилища. Иначе отозванный доступ продолжает работать в живых сессиях.
3. Подстановка `environment_variable` на выходе. Либо вернуть `apps/oma-vault` из OpenMA и научить его читать `managed_credentials`, либо написать свой прокси на хосте с проверкой `allowed_hosts` и `injection_location`. Пока его нет, учётка этого типа ничего не делает, а агент может прийти к ключу в обход.
4. Починить вкладку CLI в консоли или убрать её. Сейчас она, скорее всего, пишет в чужую таблицу, и оператор не понимает, где его учётка.

Потом.

1. Значение `injection_location` по умолчанию как в CMA и 400 при обоих выключенных местах. Клиенты SDK CMA ждут это поведение.
2. Уникальный ключ с 409 и лимит 20 учёток. Нужна открытая колонка ключа или проверка в сервисе.
3. Нормализация URL MCP при поиске учётки и обновление токена по `expires_at`, а не только по 401.
4. Читать `allowed_domains` в `web_fetch` и `web_search`. Агент бэк-офиса читает сайты поставщиков, список доменов ограничит утечку через URL.
5. Проверять `vault_ids` при создании сессии и запретить их смену обновлением.
6. Убрать токен GitHub из VM (тот же пункт в `02-environments.md`).
7. Вебхук или хотя бы событие `vault_credential.refresh_failed` и уведомление о сессии в `requires_action`. Оператору нужно знать, что агент ждёт подтверждения.
8. Бюджет сессии в рантайме. Ход на Qwen дешёвый, но зациклившийся агент тратит время VM.
9. Форма `environment_variable` и ротация OAuth в консоли, после пункта 3 из «Сначала».

Позже.

1. Политика `auto`. Ей нужен классификатор вызовов на сервере, у нас его нет.
2. `evaluated_permission` со значениями `allow` и `deny` для аудита.
3. Офлайн-проверка расшифровок задачей по расписанию поверх трассы.
4. Правило `web_fetch` только по URL из сессии.

Не нужно.

1. Убирать разархивацию хранилищ. Она удобна оператору, а секреты после пункта 2 из «Сначала» всё равно будут стёрты.
2. Ограничение по ZDR и HIPAA. Это свойство облака Anthropic, у своей копии данные и так остаются у нас.
