# Память и сновидения: разбор документации CMA и сверка с нашей копией

Разбор двух страниц Claude Managed Agents (CMA) о памяти агентов и о сновидениях (Dreams). Пути к коду ниже даны от папки `platform/`. Код проверен на ветке `feat/agent-console` 17 октября 2026 года.

## 1. Коротко

Хранилище памяти в CMA это набор небольших текстовых файлов на уровне рабочего пространства. Сессия подключает его при создании, и агент видит его как папку `/mnt/memory/<имя>/`. Агент читает и пишет туда обычными файловыми инструментами, отдельных инструментов памяти нет. Каждое изменение файла даёт неизменяемую версию, версии можно смотреть, откатывать вручную и стирать (redact).

Сновидение это асинхронная задача. Она берёт одно хранилище и от 1 до 100 прошлых сессий, читает их переписку и строит новое хранилище без дублей, устаревших и противоречивых записей. Исходное хранилище не меняется. Человек смотрит результат и решает, подключать его или выбросить. Расписания у сновидений нет, их запускают вызовом API.

У нас API памяти и версий повторяет CMA почти полностью, консоль памяти тоже готова. Главные пробелы в памяти такие. Агент не получает в системном промпте заметку о подключённых хранилищах. Путь `mount_path` в ответе API может не совпасть с реальной папкой в VM. Лимиты 8 хранилищ на сессию и 10 000 файлов на хранилище не проверяются. API сновидений тоже есть, но наш конвейер не читает переписку сессий. Он получает только их id и заголовки и делает один вызов модели. Страницы сновидений в консоли нет.

## 2. Что говорит документация

### 2.1 Страница «Using agent memory» (бета)

Страница объясняет, как дать агенту память между сессиями, как подключить хранилище к сессии, как агент с ним работает, как править память через API и как вести аудит изменений.

Объекты и поля.

| Объект | Префикс id | Поля, которые важны |
|---|---|---|
| Хранилище (memory store) | `memstore_` | `name`, `description` (её читает агент), `metadata`, `archived_at`, `created_at` |
| Память (memory) | `mem_` | `path`, `content`, `content_sha256`, `content_size_bytes`; в списке ещё бывает `memory_prefix` (папка) |
| Версия (memory version) | `memver_` | `operation` (`created`, `modified`, `deleted`), `created_by` (`session_actor`, `api_actor`, `user_actor`), `content`, `redacted_at`, `redacted_by` |
| Ресурс сессии `memory_store` | нет | `memory_store_id`, `access` (`read_write` по умолчанию или `read_only`), `instructions` до 4096 символов, в ответе `mount_path` |

Как агент читает и пишет память.

- Хранилище подключают только в `resources` при создании сессии. Добавить или убрать его у живой сессии нельзя.
- Папка называется по имени хранилища в виде slug. Имя приводят к нижнему регистру, а любые группы прочих символов заменяют одним дефисом. Точный путь берут из `mount_path`, сами его не собирают.
- Агент работает через обычный набор инструментов (`bash`, `read`, `write`, `edit`, `glob`, `grep`). Набор инструментов агента должен быть включён.
- В системный промпт сам добавляется короткий абзац о каждом хранилище. В нём имя, путь, режим доступа, `description` и `instructions`.
- Режим `read_only` держит файловая система. Запись в `read_write` создаёт версию с автором `session_actor`.
- В ленте событий это обычные `agent.tool_use` и `agent.tool_result`.
- На своих песочницах (self-hosted) папка это локальная копия. Воркер сверяет её с хранилищем после вызовов инструментов, не чаще раза в 15 секунд, и ещё раз в конце сессии. При конфликте побеждает хранилище.
- Документация прямо предупреждает. Если агент читает чужие данные, инъекция в промпт может записать мусор в память, и следующие сессии примут его за правду. Для справочных данных берите `read_only`.

Эндпоинты. Все под заголовком `anthropic-beta: agent-memory-2026-07-22`.

| Метод и путь | Что делает |
|---|---|
| `POST /v1/memory_stores` | создать хранилище |
| `GET /v1/memory_stores` | список, фильтры `include_archived`, `created_at_gte`, `created_at_lte` |
| `GET`, `POST`, `DELETE /v1/memory_stores/{id}` | прочитать, изменить, удалить вместе со всеми файлами и версиями |
| `POST /v1/memory_stores/{id}/archive` | архив, только чтение, к новым сессиям не подключить, обратного пути нет |
| `GET /v1/memory_stores/{id}/memories` | список, `path_prefix` (с `/` на конце, совпадение по целым сегментам), `depth` 0 или 1, `view` basic или full |
| `POST /v1/memory_stores/{id}/memories` | создать по пути; занятый путь даёт 409 `memory_path_conflict_error` с `conflicting_memory_id` |
| `GET /v1/memory_stores/{id}/memories/{mem}` | прочитать с содержимым |
| `POST /v1/memory_stores/{id}/memories/{mem}` | изменить текст или путь; `precondition` с `content_sha256`, при расхождении 409 `memory_precondition_failed_error` |
| `DELETE /v1/memory_stores/{id}/memories/{mem}` | удалить, можно с `expected_content_sha256` |
| `GET /v1/memory_stores/{id}/memory_versions` | история, новые сверху, фильтры `memory_id`, `operation`, `session_id`, `api_key_id`, даты |
| `GET /v1/memory_stores/{id}/memory_versions/{ver}` | версия с полным текстом |
| `POST /v1/memory_stores/{id}/memory_versions/{ver}/redact` | стереть текст, путь и хэш версии, автор и время остаются |

Для изменения памяти страница показывает `POST`, а справочник из комплекта skill называет `PATCH`. Наш маршрут принимает `POST`.

Лимиты и правила.

- Один файл памяти до 100 КБ, это около 25 тысяч токенов.
- В хранилище до 10 000 файлов. Дальше запись новых файлов падает, старые можно читать и править.
- К сессии можно подключить до 8 хранилищ.
- Версии живут 30 дней, но последние версии живого файла хранятся всегда. Версии принадлежат хранилищу и переживают удаление файла.
- Отдельного эндпоинта отката нет. Читают нужную версию и записывают её текст обратно.
- Текущую (головную) версию живого файла стереть нельзя. Сначала пишут новую версию или удаляют файл.
- Заголовки `agent-memory-2026-07-22` и `managed-agents-2026-04-01` нельзя слать вместе в запросе к хранилищу, будет 400. Подключение к сессии идёт под `managed-agents-2026-04-01`.
- Справочник skill добавляет правило. Ключи и пароли в память не кладут, иначе они попадут в каждую следующую сессию.

Советы страницы на случай роста. Делать узкие хранилища, чистить старое, запускать сновидение, заводить новое хранилище и подключать старое только на чтение.

### 2.2 Страница «Dreams» (research preview)

Сновидения дают по запросу через форму. Задача сновидения в том, чтобы убрать накопленный за много сессий беспорядок в памяти. Это дубли, противоречия и устаревшие записи. Кроме того, оно вытаскивает из переписки новые выводы.

Входы, выходы, расписание.

- На входе ровно одно хранилище памяти и список из 1..100 сессий по id. Окна по датам нет, сессии выбирают сами. Если хранилища ещё нет, создают пустое.
- На выходе новое отдельное хранилище. Его id появляется в `outputs` вскоре после перехода в `running`, когда конвейер скопировал исходное хранилище. Пока копия не готова, `outputs` бывает пустым.
- Входы сновидение не меняет и не удаляет.
- Расписания нет. Это разовая асинхронная задача, она идёт от минут до нескольких часов в зависимости от числа сессий.
- Поле `instructions` задаёт общее направление, например на чём сосредоточиться и что не трогать. Точечные правки вида «замени строку X» оно обычно не выполняет, для них есть API памяти.

Объект `dream`.

| Поле | Смысл |
|---|---|
| `id` | `drm_...` |
| `status` | `pending`, `running`, `completed`, `failed`, `canceled` |
| `inputs` | `{type: memory_store, memory_store_id}` и `{type: sessions, session_ids}` |
| `outputs` | `{type: memory_store, memory_store_id}` |
| `model` | `{id}`; в превью девять моделей, среди них `claude-opus-5-5` и `claude-sonnet-4-6` |
| `instructions` | строка до 4096 символов или null |
| `session_id` | служебная сессия конвейера; её события можно читать вживую, после конца её архивируют |
| `usage` | `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`; растёт по ходу работы |
| `error` | `{type, message}` или null |
| `created_at`, `ended_at`, `archived_at` | время |

Эндпоинты. Нужен заголовок `dreaming-2026-04-21`, одного `managed-agents-2026-04-01` мало.

| Метод и путь | Что делает |
|---|---|
| `POST /v1/dreams` | создать, ответ это полный объект со статусом `pending` |
| `GET /v1/dreams` | список без архивных, новые сверху, `limit` 20 по умолчанию и до 100, курсор `page`, `include_archived` |
| `GET /v1/dreams/{id}` | прочитать, так и опрашивают ход работы |
| `POST /v1/dreams/{id}/cancel` | из `pending` или `running` в `canceled`; повтор ничего не делает; для `completed` и `failed` ответ 400 |
| `POST /v1/dreams/{id}/archive` | только для конечных статусов, ставит `archived_at`, статус не меняет; для `pending` и `running` ответ 400; разархива нет |

Статусы и сбои.

- При `failed` и `canceled` выходное хранилище остаётся с тем, что успели записать.
- После отмены `usage` ещё несколько секунд может расти.
- Если во время работы архивировать или удалить входное хранилище или удалить входную сессию, сновидение упадёт.
- Коды ошибок: `timeout`, `internal_error`, `memory_store_org_limit_exceeded`, `input_memory_store_too_large`, `input_memory_store_unavailable`, `input_session_unavailable`.
- Оплата идёт по обычным ценам токенов выбранной модели. Цена растёт примерно линейно с числом и длиной сессий. Документация советует начать с малой пачки.
- На создание сновидений действуют стандартные лимиты частоты запросов.

Как смотреть результат. Ждут `completed`, берут `memory_store_id` из `outputs` и читают хранилище через API памяти или консоль. Дальше два пути. Хранилище подключают к новым сессиям вместо старого или рядом с ним. Либо его удаляют или архивируют. Архив самого сновидения выходное хранилище не трогает.

## 4. Что добавить

Сначала.

1. Заметка о памяти в системном промпте. Сейчас агент не знает, что у него есть память, какое у неё описание и какие `instructions` дал оператор. Без этого бэк-офис не может сказать агенту «сверяйся с правилами клиента перед ответом». Сделать это можно рядом с `buildNodeManagedSkillReminders`.
2. Один путь в VM. Монтировать папку по тому же slug, что отдаёт `mount_path`. Хранилище «Правила клиента» сейчас получит в API один путь, а в VM другой, и агент может искать не там.
3. Переписка сессий в сновидении. Нужно передавать в куратор события сессий, хотя бы сообщения пользователя и ответы агента, с обрезкой по объёму. Без этого сновидение только перекладывает старые записи и ничего не узнаёт из работы операторов.
4. Лимиты на входе `/v1/dreams` и в памяти. Это до 100 сессий, `instructions` до 4096 символов и список моделей из настроек. Плюс до 8 хранилищ на сессию и до 10 000 файлов в хранилище. Правки дешёвые, а без них один запрос может съесть бюджет токенов или забить базу.

Потом.

5. Страница сновидений в консоли. Нужны запуск с выбором хранилища и сессий, список со статусом и токенами, переход в выходное хранилище и кнопки отмены и архива. Клиент API уже есть. Для бэк-офиса это главный способ проверять, что агент запомнил, до того как память попадёт в работу.
6. Автор версии `session_actor`. В аудите бэк-офиса нужно видеть, какая сессия записала факт, чтобы найти источник ошибки или инъекции.
7. Устойчивый запуск сновидений. Нужна очередь в базе или проход по зависшим `pending` и `running` при старте. Иначе перезапуск сервера оставляет задачи висеть.
8. Коды ошибок и `session_id` как в CMA. Клиенты на SDK смогут различать причины сбоя, а оператор сможет смотреть ход работы.
9. Многошаговый конвейер. Обрабатывать хранилище частями, чтобы большое хранилище не упиралось в 8192 токена ответа.

Позже.

10. Чистка `managed_memory_versions` старше 30 дней с сохранением последних версий живых файлов.
11. Сервер должен запрещать redact головной версии, а не только консоль.
12. Коды 400 вместо 409 для отмены и архива сновидения, если важна точная совместимость с SDK.
13. Ночное сновидение по сессиям за день, например через расписание развёртываний. В CMA этого нет, но бэк-офису удобно.
14. Поле `instructions` в форме подключения памяти в консоли.

Не нужно.

- Убирать разархив хранилища не обязательно. Это удобство сверх CMA и SDK оно не ломает.
- Старые маршруты `/v1/oma/...` для памяти и сновидений повторяют `/v1`. Их лучше убрать отдельной задачей, чем развивать.
