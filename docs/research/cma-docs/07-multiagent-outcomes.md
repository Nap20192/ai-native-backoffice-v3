# CMA, раздел 7: мультиагент, outcomes, workflow runs

Разбор трёх страниц документации Claude Managed Agents (CMA) и сверка с нашей копией Open Managed Agents в `platform/`. Пути в разделе 3 даны от `platform/`. Ход ведёт Pi, области ACP, карточек harness и моста CLI не разбирались: их сейчас удаляют.

## 1. Коротко

- В CMA агент сессии может отдать работу другим агентам тремя путями: субагенты, workflow runs и советник (advisor). Всё настраивается в блоке `multiagent` агента. Новый тип блока `multiagent_20261001`, старый `coordinator` API тоже принимает.
- Outcome задаёт цель сессии: описание и рубрика в markdown. Отдельный грейдер проверяет работу по рубрике, агент правит, круг повторяется до успеха или до `max_iterations` (по умолчанию 3, не больше 20).
- Workflow run это программа, которую пишет сам агент. Она запускает в фоне до 1000 агентов фазами и сводит их ответы. Своего эндпоинта нет, run виден только по событиям `workflow_run.*`.
- У нас есть старый тип `coordinator`: ростер до 20 агентов, `self`, потоки сессии с API и переключателем в консоли. Делегирование работает через инструмент `call_agent_<id>`, но блокирует ход и не умеет дописать тому же субагенту.
- Outcomes у нас работают на main-node: событие, цикл оценки, `outcome_evaluations` в сессии, диалог в консоли. Слабые места: рубрика файлом не читается, грейдер видит только JSON событий, а не файлы результата.
- Нашли поломку. Консоль шлёт `session_thread_id` в `user.tool_confirmation` для потока субагента, а схема сервера такое поле не знает и отвечает 400.
- Advisor и inline-агенты в коде есть, но во время хода не работают. Workflow runs нет совсем.

## 2. Страницы

### 2.1 Мультиагентная оркестровка (multiagent-orchestration)

Страница описывает, как агент сессии делит работу. Решает агент, вы только разрешаете пути и подсказываете в системном промпте, когда их брать.

| Путь | Что происходит | Когда брать | Ограничения |
|---|---|---|---|
| Субагенты | агент сам раздаёт задачи и читает отчёты, у каждого субагента свой поток | нужны специалисты со своими промптами и инструментами, нужен повторный вопрос тому же субагенту | один уровень, до 25 дочерних потоков на сессию, простаивающие тоже считаются |
| Dynamic workflows | агент пишет программу, сервер гоняет её в фоне как один run | много кусков, параллельная или долгая работа: аудит, миграция, сверка | каждый агент run тратит токены, нужен бюджет сессии |
| Advisor | основной поток советуется с более сильной моделью посреди хода | работу делает один агент, нужен взгляд со стороны на план или итог | советоваться может только основной поток, оплата по ценам модели советника |

Блок `multiagent` типа `multiagent_20261001` держит три настройки. Каждая включается и выключается отдельно.

| Настройка | Что включает | Список агентов | По умолчанию |
|---|---|---|---|
| `subagents` | делегирование своим агентам и тем, кого агент описал сам | `subagents.predefined_agents`, до 20 | включено |
| `workflows` | dynamic workflows | `workflows.predefined_agents`, до 20 | включено |
| `advisor` | советник | нет, задают `model` | выключено |

Агенты бывают двух видов. Predefined это уже созданный агент, он работает со своей моделью, промптом, инструментами, MCP и навыками. Inline агент описывается на ходу, без сохранения, и берёт модель, инструменты, MCP и навыки агента сессии. Флаг `inline_agents: {"type": "disabled"}` оставляет только список. Тогда в списке нужен хотя бы один агент, иначе 400.

Запись в списке бывает четырёх форм: строка с id, `{type: "agent", id}`, `{type: "agent", id, version}`, `{type: "self"}`. Без `version` ссылка закрепляется на текущей версии в момент сохранения агента и потом не меняется. `self` даёт копии самого агента, переопределения сессии действуют и на них.

Правила для обоих списков:

- агент с собственным блоком `multiagent` в список не входит, 400;
- до 20 разных агентов в каждом списке, копий одного агента можно запускать сколько угодно в пределах лимита потоков;
- у всех агентов одинаковый `inference_geo` или ни у кого, иначе 400;
- префикс `ant__` в именах своих инструментов занят, с ним правка агента и новая сессия дают 400;
- при окружении с сетью `limited` MCP-хост любого агента из списков должен быть в `allowed_hosts`, иначе создание сессии даёт 400. Проверку снимает `allow_mcp_servers: true`.

Все агенты сессии делят одну песочницу, файлы и учётные данные из vault. История разговора у каждого своя, в своём потоке. Основной поток это общий поток событий сессии. Поток субагента живёт, пока его не заархивируют, поэтому агент может дописать ему ещё. MCP-серверы привязаны к агенту, а vault к сессии: ключ нужен для каждого MCP-сервера всех агентов.

Правка блока того же типа меняет только присланное. Пропущенное поле хранит старое значение, `null` сбрасывает на умолчание, присланный список заменяет старый, настройка с другим `type` заменяется целиком. Сессия копирует настройки при создании, правка агента её не трогает.

Советник задаётся как `{"type": "enabled", "model": "..."}`, других полей нет. Модель агента не должна быть сильнее советника, неверная пара даёт 400 при сохранении и при создании сессии. Каждая консультация идёт отдельным потоком с зарезервированным именем `anthropic.advisor`. События идут так: `session.thread_created`, `session.thread_status_running`, `agent.thread_message_received` с советом, `session.thread_status_idle`, `session.thread_status_terminated`. Совет может прийти позже, чем idle потока. Часть моделей отдаёт клиенту только заглушку `redacted`, агент при этом читает совет целиком. Сбой консультации ход не ломает. Потоки советника не входят в лимит 25.

Старый тип `coordinator` держит список в поле `agents` и умеет только субагентов и советника. Переход на новый тип идёт одной правкой всего блока: пропущенное получает умолчание, то есть workflows и inline-агенты включатся сами.

Справочник скилла claude-api пока описывает старый тип `coordinator`. Из него полезны детали, которых нет на странице:

| Что | Подробности |
|---|---|
| Эндпоинты потоков | `GET /v1/sessions/{id}/threads`, `GET .../threads/{tid}`, `POST .../threads/{tid}/archive`, `GET .../threads/{tid}/events`, `GET .../threads/{tid}/stream` |
| Статусы потока | `running`, `idle`, `rescheduling`, `terminated`. Сессия `running`, пока работает хоть один поток |
| События | `session.thread_created`, `session.thread_status_running`, `_idle`, `_rescheduled`, `_terminated`, `agent.thread_message_sent`, `agent.thread_message_received` |
| Инструменты координатора | `list_agents` и `send_to_agent`. Задача уходит сразу, отчёт приходит в следующем ходе |
| Подтверждения | запрос из потока субагента дублируется в основной поток с `session_thread_id`. Ответ шлют с тем же `session_thread_id` |
| Прерывание | `user.interrupt` без `session_thread_id` останавливает все потоки, с ним только один |

### 2.2 Outcomes (define-outcomes)

Outcome говорит сессии, как выглядит готовый результат и как мерить качество. Сервер сам заводит грейдер с отдельным контекстом, чтобы решения агента на него не влияли. Грейдер пишет, какие пункты рубрики прошли и какие нет, и это уходит агенту на следующий круг.

Outcome не поле сессии. Его шлют событием в `POST /v1/sessions/{id}/events` или кладут одно такое событие в `initial_events` при создании. Отдельный `user.message` для старта не нужен.

| Поле `user.define_outcome` | Тип | Смысл |
|---|---|---|
| `description` | строка | задача, к которой идёт агент |
| `rubric` | `{type: "text", content}` или `{type: "file", file_id}` | обязательна, markdown с проверяемыми пунктами. Файл грузят через Files API и берут в разных сессиях |
| `max_iterations` | число | по умолчанию 3, максимум 20 |

Сервер возвращает событие с `outcome_id` (`outc_...`) и `processed_at`. Активен один outcome за раз. Следующий шлют после финального `span.outcome_evaluation_end`, история прошлого outcome остаётся в сессии.

| Событие | Поля | Смысл |
|---|---|---|
| `span.outcome_evaluation_start` | `outcome_id`, `iteration` с нуля | грейдер начал оценку круга |
| `span.outcome_evaluation_ongoing` | `outcome_id`, `iteration` | пульс, мысли грейдера не видны |
| `span.outcome_evaluation_end` | `outcome_evaluation_start_id`, `result`, `explanation`, `iteration`, `usage` | оценка круга закончена |

| `result` | Что дальше |
|---|---|
| `satisfied` | сессия уходит в `idle` |
| `needs_revision` | агент начинает новый круг |
| `max_iterations_reached` | оценок больше нет, агент делает один последний ход и сессия уходит в `idle` |
| `failed` | рубрика не подходит к задаче, например противоречит описанию. Сессия уходит в `idle` |
| `interrupted` | пришёл `user.interrupt`, даже если оценка ещё не началась. Тогда `outcome_evaluation_start_id` пустая строка |

Статус можно опрашивать через `GET /v1/sessions/{id}`: массив `outcome_evaluations[]`, до конца оценки `result` равен `pending`, `running` или `evaluating`. Результат агент пишет в `/mnt/session/outputs/`. Файлы забирают через `GET /v1/files?scope_id=<session_id>`, этому запросу нужен бета-заголовок. Файл появляется в списке через несколько секунд после idle.

Справочник скилла добавляет: на `needs_revision` сессия продолжает работу, поэтому ждать конца надо по `session.status_idle`, а не по событию оценки. Сессия на паузе из-за бюджета не принимает новый outcome и игнорирует interrupt.

### 2.3 Workflow runs (workflow-runs)

Workflow это программа, которую агент пишет под задачу. Run это одно её исполнение. Сервер гоняет run в фоне, агент тем временем отвечает пользователю или заканчивает ход. Отдельного вызова API для старта нет: агент решает сам по `user.message` и системному промпту. Шага одобрения перед стартом тоже нет.

Run делится на фазы, в каждой фазе программа запускает агентов в своих потоках. Программа умеет запускать агентов параллельно, передавать ответ одного агента другому, повторять шаг до прохождения проверки. Если агент упал, сервер обычно запускает его ещё раз в новом потоке. Второй сбой программа обрабатывает сама или завершает run.

Состояния run: running, idle (пауза, например на бюджете), ended. Run открыт от `workflow_run.created` до `workflow_run.status_ended`.

| Событие | Когда | Поля |
|---|---|---|
| `workflow_run.created` | агент запустил run | `workflow_run_id` (`wrun_...`), `name`, `description`, `phases[]` с `id` (`wrph_...`), `name`, `description` |
| `workflow_run.status_running` | run начал работу или продолжил после паузы | |
| `workflow_run.status_idle` | пауза, причину не пишет | |
| `workflow_run.phase_started`, `workflow_run.phase_ended` | вход и выход из фазы | `workflow_run_phase_id`, у конца ещё `phase_started_id` |
| `workflow_run.status_ended` | run закончен, всегда последнее событие run | `result` |
| `workflow_run.error` | ошибка run или отказ в старте | `error.type`, `error.message`. Без run `workflow_run_id` равен `null` |

| `result` | Смысл |
|---|---|
| `completed` | программа дошла до конца. Это не значит, что работа прошла проверку |
| `stopped` | агент остановил run или сессию заархивировали |
| `error` + `timeout_error` | истёк срок жизни run |
| `error` + `program_error` | упал код программы или упавший поток завершил run |
| `error` + `thread_limit_error` | превышен лимит агентов на run |
| `error` + `unknown_error` | сервер не смог продолжить или сработал другой лимит |

| Лимит | Значение |
|---|---|
| Потоков одновременно в одном run | 64 |
| Агентов за всю жизнь run | 1000, дальше `thread_limit_error` |
| Срок жизни run | 24 часа или срок, который задал агент. Пауза срок не останавливает |
| Открытых run в сессии | 10, дальше `workflow_run.error` с `max_workflow_runs_error` |
| `name` и `description` | сервер режет до 64 и 256 символов |

Потоки run несут тот же `workflow_run_id`, сервер сам их архивирует к концу run. Они не входят в лимит 25 дочерних потоков. Потоки run работают в общей песочнице. Run может создать два потока на одну работу, поэтому инструменты должны выдерживать повторный вызов. Вложенных run нет, их запускает только основной поток.

`user.interrupt` останавливает ход агента, но не run. Чтобы остановить run, просят агента сообщением. Пока run открыт, архив и удаление сессии могут дать 400 с `workflow_run_open`, архив потока run и смена `agent` сессии дают 400 всегда. На вызовы инструментов из потоков run отвечают сразу, не дожидаясь idle. Работа готова, когда у каждого run есть `status_ended` и после этого пришёл `session.status_idle` с `end_turn`. Пока run открыт, оценка outcome не начинается.

Поток событий не повторяет пропущенное. После переподключения состояние собирают из списка событий с фильтром `types[]`, эндпоинта со списком run нет. Расход run считают по `usage` его потоков. События run не вызывают webhooks. При лимите частоты поток получает `session.error` с `retry_status` `retrying` или `exhausted`.

## 4. Что добавить

1. Сначала. Принять `session_thread_id` в `user.tool_confirmation` и `user.custom_tool_result`. Сейчас подтверждение вызова в потоке субагента из консоли падает с 400, поток висит в `requires_action`. Правка в одной схеме.
2. Сначала. Читать рубрику из файла и для агента, и для грейдера. Бэк-офис держит типовые рубрики (сверка отчёта, акт, выгрузка) и берёт их в разных сессиях и deployment.
3. Сначала. Давать грейдеру файлы из `/mnt/session/outputs` с лимитом размера и снимать обёртку блока кода с ответа судьи. Результат бэк-офиса почти всегда файл, а оценка по одному журналу событий его не видит.
4. Потом. Довести семантику outcome: `interrupted` при любом прерывании, последний ход после `max_iterations_reached`, 400 на второй outcome, пока первый активен. Без этого клиенты на SDK ждут не тех событий.
5. Потом. Сделать делегирование как в CMA: задача уходит сразу, отчёт приходит отдельным ходом, тому же потоку можно дописать. Поднять лимит до 25 и считать все дочерние потоки. Длинная сверка не будет держать ход основного агента.
6. Потом. Решить судьбу `enable_general_subagent`: подключить как inline-агента или убрать из API и формы. Сейчас флаг обещает то, что не работает.
7. Потом. Включить проверку бюджета сессии. Без неё мультиагент и любые фоновые run опасны по расходам.
8. Позже. Принять тип `multiagent_20261001` и сводить его к нашему ростеру, когда поднимем SDK выше 0.120. Пока клиентов на новом типе нет.
9. Позже. Советник. Для бэк-офиса это проверка плана и итога сильной моделью, но нужна таблица пар моделей и отдельный поток.
10. Позже. Workflow runs. Массовая обработка сотен документов бэк-офису полезна, но это свой исполнитель программ, фазы, лимиты и бюджет. Начинать стоит после пунктов 5 и 7.
