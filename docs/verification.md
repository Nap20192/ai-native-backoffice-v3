# Как я отчитываюсь и как проверяется работа

Черновик 1, 2026-10-15.

Продукт: корпоративная платформа, в которой работают агенты. Главный путь такой: задание из таск-менеджера → агент в пределах своей компетенции открывает сессию и готовит всё нужное → сотрудник продолжает ту же сессию и доделывает работу. Агентов собирают в конструкторе как в Claude Managed Agents: скиллы, workflow, сабагенты, MCP-инструменты. Пользуются ими многие люди.

Цель документа: чтобы владелец в любой момент понимал, что сделано и что проверено, и не перепроверял руками.

## 1. Правило честности

Каждое утверждение в отчёте имеет одну из трёх меток:

| Метка | Значит |
|---|---|
| **Проверено тестом** | Есть автоматический тест или сценарий, он зелёный, его можно перезапустить одной командой |
| **Проверено вживую** | Прогнано на настоящей модели или в браузере, приложены артефакты: трасса, скриншот, лог |
| **Не проверено** | Сделано, но доказательства нет. Сказано почему и что нужно для проверки |

Без метки утверждение в отчёт не попадает. Если тест красный, это пишется в начале отчёта, а не в конце.

## 2. Уровни проверки

От дешёвого к дорогому. Нижние уровни прогоняются на каждое изменение, верхние на каждую веху.

| Уровень | Что проверяет | Чем | Модель | Когда |
|---|---|---|---|---|
| 1. Unit | Логика: права, очередь, аренда, версии агентов | Тесты пакетов, строгий TDD (красный → зелёный) | Нет | Каждое изменение |
| 2. Контракты | API совпадает с OpenAPI, события со схемами | Проверка схем, тесты API | Нет | Каждое изменение |
| 3. Сценарии | Сквозные истории продукта на всём стеке | Исполняемые сценарии (раздел 3) | **Фейковая модель** с записанными ответами | Каждое изменение |
| 4. Надёжность | Падения, повторы, дубли, гонки | Сценарии с убийством процесса посреди хода | Фейковая | Каждая веха |
| 5. Безопасность | Права, утечки, изоляция, prompt injection | Матрица прав, канарейки секретов, набор атак | Фейковая и живая | Каждая веха |
| 6. Качество агентов | Агент реально справляется с задачами | Evals: набор задач + проверяющий по критериям | **Живая** | Каждая веха, с лимитом бюджета |
| 7. Интерфейс | Экраны работают и выглядят прилично | Playwright: сценарии и скриншоты 1280 и 390 | Фейковая | Каждое изменение UI |
| 8. Нагрузка | Много людей и агентов одновременно | Скрипт нагрузки (k6 или свой) | Фейковая | Перед демо |

Фейковая модель отвечает заранее записанными репликами и вызовами тулов. Поэтому сценарии детерминированы, бесплатны и не зависят от сети. Живая модель включается флагом `LIVE_AGENT=1` и только на уровне 6 и в живом прогоне вехи.

## 3. Сценарии приёмки

Каждый сценарий — исполняемый файл. Он поднимает стек, выполняет шаги и проверяет результат в базе, журнале и интерфейсе. Список растёт вместе с продуктом.

| # | Сценарий | Что доказывает |
|---|---|---|
| S1 | Создать агента в конструкторе: инструкции, скилл, MCP-сервер, сабагент; опубликовать v1 | Конструктор работает, версия неизменяема |
| S2 | Задание из таск-менеджера → агент открывает сессию и готовит черновик → сотрудник открывает ту же сессию и дописывает | Главный путь продукта |
| S3 | Сотрудник пишет агенту в мессенджере, агент вызывает тул через MCP | Канал мессенджера и Hub |
| S4 | Два сотрудника с разными правами просят одного агента об одном и том же | Права = агент ∩ человек |
| S5 | Убить воркер посреди хода | Ход продолжается, тул не вызван дважды, клиент не потерял события |
| S6 | Write-действие ждёт подтверждения, человек подтверждает через час | Ожидание переживает перезапуск, действие выполнено ровно один раз |
| S7 | Агент с сабагентами и workflow по расписанию | Workflow, сабагенты, расписание |
| S8 | Агент пытается вывести секрет наружу и прочитать чужую сессию | Секрет не утёк, чужое не прочитано |
| S9 | Опубликовать v2 агента, пока идут сессии на v1, затем откат | Версии не ломают идущую работу |
| S10 | 50 сотрудников и 10 агентов одновременно | Очередь и аренда держат нагрузку |

## 4. Инструменты проверки

| Инструмент | Зачем |
|---|---|
| `make verify` (или `task verify`) | Одна команда: unit, контракты, сценарии на фейковой модели, линтеры. Выход: зелёный или красный и путь к отчёту |
| `make verify-live` | Живая модель: evals и сценарии S2, S3, S7 с бюджетом на прогон |
| Фейковая модель | Сервер, совместимый с API модели, с записанными ответами. Записи делаются с живых прогонов |
| Экспорт трассы | Любая сессия выгружается: журнал, вызовы тулов, стоимость. Прикладывается к отчёту как доказательство |
| Канарейка секретов | В vault кладётся уникальная строка. После прогона ищем её в журнале, логах, ответах модели и файлах песочницы. Найдена — тест красный |
| Матрица прав | Таблица «человек × агент × тул → ожидаемый результат», по ней генерируются тесты |
| Набор атак | Prompt injection в задании, в файле, в ответе MCP. Агент не должен выполнить чужую инструкцию |
| Хаос-скрипт | Убивает воркер, рвёт соединение, перезапускает базу посреди сценария |
| Evals | Задачи по ролям (HR, проекты, документы) с критериями. Проверяющая модель ставит оценку, результат хранится по версии агента, видна динамика |
| Playwright | Сценарии интерфейса и скриншоты 1280 и 390 для отчёта |

## 5. Формат отчёта

Отчёт пишется на каждую веху и по запросу. Лежит в `docs/reports/ГГГГ-ММ-ДД-<веха>.md` и дублируется в опубликованную страницу статуса (Artifact), чтобы его можно было открыть в Claude desktop. Диаграммы в отчётах рисуются картинками, а не mermaid.

```
# Веха: <название>        Дата        Итог: зелёный | есть красное

## Коротко
2-3 предложения: что теперь умеет продукт.

## Что сделано
- <пункт> — Проверено тестом (`<тест>`) | Проверено вживую (<артефакт>) | Не проверено (почему)

## Демо
Скриншоты 1280 и 390, ссылки на трассы сессий.

## Цифры
Тесты: N зелёных, M красных. Сценарии: S1..Sn. Evals: оценка по агентам и изменение.
Стоимость живых прогонов. Время хода (p50, p95).

## Что не работает или не проверено
Список с причинами.

## Нужны решения владельца
Не больше 3 вопросов, по каждому моя рекомендация.

## Дальше
Что делаю в следующей вехе.
```

Между вехами — короткие сообщения в чате: что закончил, что проверено, есть ли блокер. Без простыней.

## 6. Ворота вехи

Веха закрыта, только если:

1. `make verify` зелёный.
2. Все сценарии вехи проходят на фейковой модели.
3. Главный сценарий вехи прогнан вживую, трасса приложена.
4. Канарейка секретов и матрица прав зелёные.
5. Скриншоты интерфейса приложены, если менялся UI.
6. Отчёт написан по формату, у каждого пункта есть метка.

## 7. Порядок работы

- Строгий TDD: первым коммитом идут падающие тесты, потом код.
- Каждая ручная проверка превращается в перезапускаемый тест или скрипт.
- Независимый ревью перед слиянием: отдельный агент проверяет изменение по спеке и по стандартам.
- Параллельная работа идёт в отдельных worktree. Сливаю и проверяю я как координатор.
- Тяжёлые прогоны (кластер, нагрузка, живая модель) запускаются по одному, с контролем нагрузки на ноутбук.

## 8. Первая веха: выбор основы

До кода продукта выбираем основу, и выбор тоже проверяется, а не обсуждается.

| Кандидат | Что проверяем |
|---|---|
| OpenMA (self-host, Postgres) | S1 (агент в консоли), S3 (MCP), S5 (убить процесс посреди хода) |
| QM + персоны из `qm-multi-agent` | S4 (агент от имени человека), S5, сколько работы до конструктора агентов |
| Своё тонкое ядро по схеме QM + модель агентов OpenMA | Оценка объёма работы по результатам двух прогонов выше |

Результат: отчёт вехи с таблицей «требование → кандидат → проверено или нет» и рекомендацией.
